# 3.3.6 Formats Implementation Plan

> TDD (superpowers:test-driven-development). Part of `docs/roadmap.md`, release 3.3, item 3.3.6. Related: #107.

**Goal:** Consumers control how times and dates are written in the gutter, on event bars, in day headers and in the
toolbar title, with the same option shape the convention uses, without changing anything for current users.

## The standard (FullCalendar v7.1.1 source, `packages/preact/src/`)
- Names in v7: `slotHeaderFormat` (gutter labels; v6's `slotLabelFormat` is NOT accepted, `options.ts:285`,
  `reducers/CalendarDataManager.ts:722-737`), `eventTimeFormat`, `displayEventTime`, `displayEventEnd`,
  `dayHeaderFormat`, `titleFormat`. https://fullcalendar.io/docs/slotHeaderFormat
- Accepted forms: `Intl.DateTimeFormatOptions` object (+ extras like `meridiem`, `omitZeroMinute`), a string (needs a
  formatting plugin) or a function (`datelib/formatting.ts:10-27`).
- 12h/24h is decided by the locale through Intl unless the format sets `hour12`/`hourCycle`.
- `displayEventTime` defaults true; all-day events never get time text; the end time shows only when the event has an
  explicit end (`component-util/event-rendering.ts:317-372`).

## Decisions (record)
- Accept **`Intl.DateTimeFormatOptions` only** in 3.3 (no strings — ilamy has no formatting plugin; no functions —
  `renderHour`/`renderEvent` already cover custom rendering). The FullCalendar extras (`meridiem`,
  `omitZeroMinute`, …) are not supported; say so in TSDoc.
- **Defaults reproduce today's output exactly.** When an option is unset, render as now (including `timeFormat`
  '12-hour'/'24-hour'). When set, format with `Intl.DateTimeFormat(locale, { ...options, timeZone })` using the
  calendar's `locale` and `timezone`. If the consumer's options omit `hour12`/`hourCycle`, apply the `timeFormat`
  shorthand, so `timeFormat` keeps meaning something.
- Precedence: `renderHour` (existing render prop) beats `slotHeaderFormat`; `renderEvent` beats `eventTimeFormat`.
- `displayEventTime` (default true) / `displayEventEnd` (default: today's behaviour per view — read the code and keep
  it) control the default event content only.

## API
```ts
slotHeaderFormat?: Intl.DateTimeFormatOptions
eventTimeFormat?: Intl.DateTimeFormatOptions
displayEventTime?: boolean
displayEventEnd?: boolean
dayHeaderFormat?: Intl.DateTimeFormatOptions
titleFormat?: Intl.DateTimeFormatOptions
```

## Where (verify): the existing date/time formatting hook (`useDateTimeFormatters` per `.agents/rules/code-style.md`;
find it), `components/hour-label.tsx`, `components/draggable-event/default-event-content.tsx`, the day header
components in `components/views/` and `header/` (title). Remember the configured dayjs and `docs/timezones.md`:
format the instant in the calendar's zone. Harness query params for each (JSON in the URL is fine, e.g.
`&eventTimeFormat={"hour":"2-digit","minute":"2-digit","hour12":false}`) in `apps/e2e/src/harness-config.ts`.

## Tests first
Unit: each option changes exactly its target and nothing else; unset options render byte-identical to before (snapshot
the text of a week, day, month and resource view header/gutter/bar before your change and compare); `timeFormat`
fills `hour12` when absent; locale `de-DE` + `timezone` applied; all-day events get no time text;
`displayEventEnd:false` hides the end.
e2e: week view with `eventTimeFormat` 24h two-digit shows "09:30"; `slotHeaderFormat` changes gutter labels;
`dayHeaderFormat {weekday:'long'}` shows "Wednesday"; `titleFormat` changes the toolbar title; with no params, the
existing specs' text assertions still pass.

## Global constraints
No breaking change; configured dayjs only; no `!`, no `any`, `.at()`, named exports, name every condition; unit AND e2e
first; revert proof; docs (`docs/translation-usage.md` if relevant, `docs/types-and-interfaces.md`, website props page,
`docs/feature-checklist.md` tick `slotLabelFormat`/`eventTimeFormat` noting the v7 name). Public text never frames
this as parity; cite FullCalendar behaviour with file:line. No dev log, no CHANGELOG.
