# Development Log - 2026-09-11

## Changes

- **[calendar/initialDate]**: The date a calendar opens on is now resolved by the rule the configured constructor already applies, instead of treating every input as a wall clock. A string with no offset names a clock reading, so the calendar's zone anchors it and `'2025-03-10'` opens on 10 March wherever it is read; a `Date`, a `Dayjs` or an offset-carrying string already names an instant, so only the clock it renders against changes. Before this, `initialDate='2025-03-10T22:00:00.000Z'` with `timezone="Pacific/Kiritimati"` opened on the 10th from a UTC or New York machine and the 11th from Tokyo, when the instant is the 11th in Kiritimati in all three.

- **[utils/dayjs]**: Extracted the wall-clock-versus-instant test out of `timezoneAwareDayjs` as the exported `isWallClockReading`. The rule now has one definition and two callers: the constructor, which reads the module default zone, and the engine, which has the zone in hand before `setDefault` has run.

- **[calendar/engine]**: `IlamyCalendar` hands the engine the raw `initialDate` rather than a `safeDate` result, because parsing flattens away the distinction the rule turns on. `anchorInitialDate` runs once per mount via `useState` rather than on every render; the navigation slice reads it only in its lazy initializer, so later calls were discarded.

- **[docs]**: `docs/timezones.md`, `safeDate`'s doc comment and the navigation slice's comment all described the navigation slice as the place `initialDate` gets anchored. It is the engine now.

## Notes

This matches FullCalendar's `timeZone` rule, which the docs state as: a string without an offset is "parsed (and thus displayed) as if it were" in the configured zone, one with an offset is "appropriately shifted to display" in it. Verified against https://fullcalendar.io/docs/timeZone rather than from memory.

The new test is load-bearing: with the old wall-clock-for-everything branch restored it fails with `Expected "2025-03-11", Received "2025-03-10"`. The timezone block passes under UTC, Asia/Tokyo, America/New_York, Pacific/Midway and Pacific/Kiritimati.

Worth knowing for the next change here: `anchorInitialDate` takes the zone as an argument specifically because `dayjs.tz.setDefault` runs in an effect, so the module default is empty during the first render. Anything else that needs the zone during render has the same constraint.
