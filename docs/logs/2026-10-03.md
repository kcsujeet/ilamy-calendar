- **[review fixes, #308 round 3]** (head `97f5b5e`; structure, react, i18n and project-conventions passed):
  - **Bug: a resource with id 0 drew every resource's events.** `Resource.id` is `string | number`, but the cell, `useProcessedDayEvents` and `useProcessedWeekEvents` filtered with `if (resourceId)`, so 0 read as "no resource". Reproduced in the e2e harness (new `numeric-resource-ids` scenario): Room One's booking drawn twice in every horizontal and vertical day/week/month, and inside Room Zero's month cells. Pre-existing; the PR had moved the cell's copy. `filterEventsForResource` now takes `resourceId | undefined` and keeps every event when it is `undefined`, so the three callers call it unconditionally and the rule lives in one place.
  - Same bug, found by sweeping the predicate: both events layers chose the now-line dot with `!resourceId || first === resourceId`, so a resource 0 that is not first drew a second dot. Now `resourceId === undefined`. The dot carries `data-testid="current-time-dot"` (`@ilamy/ui`) so the spec can count it.
  - Tests: pipeline unit tests (0 filters like any id; `undefined` keeps all); a vertical-layer unit test for the dot (fails with the old check); e2e specs for bars in 6 view/orientation pairs, month cell placeholders, and the dot in both orientations (all failed before the fix). `use-calendar-drag.test.tsx` pins one sensor list across re-renders (fails when the options are rebuilt per render).
  - The recurrence window margin is `WINDOW_MARGIN_DAYS` shifted with `dayjs.utc(...).add/subtract`, not a hand-rolled ms product. Floating dates are UTC instants, so UTC setters keep it DST-free (verified in New York across the March change).
  - `useLatestHandler`'s stable wrapper returns `Result | undefined` instead of casting the optional call to `Result`.
  - Names: the "+N more" key check names `isEnterKey`/`isSpaceKey`; `hourly` test factory -> `mkHourlyEvent`.

- **[recurrence, #307]** Occurrences after a daylight-saving change ran an hour off whenever the calendar's `timezone` differs from the machine's zone. `fromFloatingDate` set the occurrence's fields on the series start with dayjs setters, which keep the start's UTC offset: in New York, a daily 09:00 series from 6 March 2025 came out at 14:00Z (10:00 EDT) from 9 March on. When the zones match, the instant came out right but the value kept the stale offset (`09:00-05:00` in March). It now reads the wall-clock string in the calendar's zone (the configured dayjs anchors an offset-less string there, docs/timezones.md), so the offset is the one in force that day. RFC 5545 §3.8.5.3: instances start "at the same local time regardless of time zone changes"; §3.3.5's rules for a skipped time (the offset before the gap: 02:30 -> 03:30 EDT) and a repeated one (the first, EDT) hold too, pinned by tests.
  - EXDATEs and `recurrenceId`s are written from an occurrence's start, so new edits store the corrected instants. Ones stored by earlier versions for an occurrence after a change, in a calendar whose zone differs from the machine's, hold the old shifted instant and will no longer match it.
  - Found while proving it, and verified on `main` with no plugin: on a change day the time grid draws a 09:00 event an hour off, on row 8 on 9 March 2025 (spring) and row 10 on 2 November 2025 (autumn), in week and day views, while the gutter labels row 9 "9 AM" on both days. `layoutVertical` places a bar at `event.start.diff(gridStart, 'hour', true) / totalUnits`: elapsed hours since the column's midnight over 24 slots, which is 8 or 10 hours to 09:00 on those days. Not part of this fix; filed as #311. The e2e spec compares the change day's occurrence against a one-off on the same day instead.
  - The recurrence suite already fails 20 tests on a New York machine before this change (16 after it, none new): those tests assume a UTC machine, as CI is. Not investigated further.
