# Development Log - 2026-08-14

## Changes

Audit of everything #248 changed, looking for code that still believed the old end semantics. Five findings, four user-visible. Every range query in the core funnels through `eventOverlapsRange` (`transformEvents` feeds the year view, the per-day hooks, grid cells and the all-day row), so those inherited the earlier fix correctly. These five did not.

- **[layout]**: `computeColumnSpan` resolved its span from the adjusted (exclusive) end while `isTruncatedEnd` on the next line still read the raw `end`. The two disagreed exactly at the grid's edge: an event ending at the midnight after the last day covers that day and stops, but the flag marked it as continuing, so `draggable-event` drew the overrun indicator and squared the corner. Every month row ends on a Saturday, so any multi-day event ending Sunday at midnight showed a false "continues past here". The flag now reads the same adjusted end, so the two cannot drift apart again.

- **[layout]**: The step back from an exclusive end is a **millisecond**, not a minute. A minute-sized step swallowed anything ending inside it: an event running 30 seconds into the next day lost that day entirely, and one running 30 seconds past the hour lost that row. The minute predated #248 on the hour path; this fixes both granularities. Boundary-aligned events are unaffected, since 23:59:59.999 and 23:59:00 share a `startOf('day')`.

- **[drag-and-drop]**: Removed the midnight snap in `dnd-utils`. It rewrote any end landing on midnight to the previous day's 23:59:59.999, which **resized the event on every drag** (a two-hour event became 1h59m59.999s) and reintroduced exactly the sub-second residue the form no longer produces. It existed to stop the inclusive layout painting an extra day, which the exclusive span now handles.

- **[agenda]**: `appearsOnDay` had its own overlap test using `end.isSameOrAfter(dayStart)`, so a one-day all-day event stored the conventional way was listed under **two** days while the grid showed one. Now strict, matching `eventOverlapsRange`. Its predicate stays local because it is genuinely different from a general overlap test (all-day repeats per day, timed appears once under its start day).

- **[agenda]**: `AgendaEventRow` computed `totalDays` from the raw end plus one, so a conventionally stored three-day event read "Day 1/4" and a one-day event read "Day 1/2" (and was treated as multi-day at all). It now counts to the last day the event covers.

- **[recurrence]**: `generateRecurringEvents` filtered occurrences with `end.isSameOrAfter(startDate)` while its own comment stated the rule as "event_end > range_start". The boundary occurrence was generated and then dropped again by the core's filter, so it was invisible in-app but wrong for anyone calling this exported function directly.

- **[vertical-grid]**: Comment only. It cited `startTime: 0, endTime: 0` as an example of an empty business range, which is the exact config that now means a full day.

## Notes

**Cross-surface check.** One all-day event built through the form helpers, measured on every surface at once:

```
stored          : 2026-05-13T00:00 -> 2026-05-14T00:00
month columns   : 1   truncatedEnd: false
listed on May 13: true    May 14: false
ical            : DTSTART;VALUE=DATE:20260513  DTEND;VALUE=DATE:20260514
```

Storage, layout, overlap filtering and export agree. Before these fixes they did not, and no single-file test would have shown it.

**Two of the five were duplicated logic in plugins** that never went through `eventOverlapsRange`. Fixing the core helper did nothing for them, which is why the sweep has to look for the *predicate* (`.end.isSameOrAfter(`, `.end.isSame(`, `diff(..., 'day')`) rather than for callers of a function.

**Checked and deliberately left alone**: `vertical.ts` clustering already uses `isSameOrAfter` correctly and its discrete `Math.ceil` agrees with the exclusive span; drag-to-create's `computeRange` follows the new cell contract automatically (56 tests untouched); the playground seed and `testing/generator.ts` still use `23:59`/`endOf('day')` ends, which remain correct if unconventional; events with `end < start` are still silently dropped by the multi/single partition, which is pre-existing and unrelated.

**New rule.** `.agents/rules/change-impact.md` records the method this audit should have followed from the start, with the specific shapes to sweep for. Referenced from the hard rules in `AGENTS.md`.
