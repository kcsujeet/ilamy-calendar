# Development Log - 2026-09-15

## Changes

- **[month grid]**: Fixed #246. With a timezone configured, a month grid spanning a DST transition rendered one week twice and dropped another, and events in the dropped week did not render at all. Measured on 3.0.1: 127 malformed grids of 1536 (8 zones, 2024-2027, four `firstDayOfWeek` values), every DST zone affected, UTC clean. After the fix, 0 of 1536.

- **[month grid]**: Two steps carried the receiver's UTC offset forward instead of recomputing it, and both had to be re-anchored. `getMonthWeeks` steps a week at a time; `getWeekDays` composes `startOf('week')` with `day(firstDayOfWeek)`. Removing either normalization brings the failures back, so both are load-bearing. `getMonthGridRange` derives from the same weeks, so its range now agrees with the grid it describes in all 1536 cases, which also fixes the event query and navigation that read it.

## Notes

The reporter's headline repro no longer reproduced, which is how this could have been closed by mistake. Their case (Europe/London, March 2025) returns 42 distinct days on 3.0.1, most likely fixed incidentally by #249's constructor change. The defect had simply moved: it is the autumn transitions that break, where the offset decreases and the frozen offset carries the anchor back past midnight into the previous week. A spring transition drifts the other way and stays inside the day. Sweeping 1536 grids rather than running the repro is what found it.

Their suggested one-line fix, `.startOf('day')` after the week step, was necessary but not sufficient. Sydney's October grid still failed, because `getWeekDays` drifts on its own: given a correct Monday anchor of 6 October it returned 29 September to 5 October. Both places need re-anchoring.

The reporter also pointed at `collectDaysBetween` in `@ilamy/utils/events` as a single normalised walk to reuse. It does not exist: it was part of #241, which was closed unmerged and re-done as #253 without that helper.

dayjs does not document `add` or `startOf` against DST, so the mechanism was measured instead: from a 20 October anchor in Europe/London, `add(1, 'week')` yields `2025-10-27T00:00:00+01:00`, an instant that is 26 October 23:00 in London, and `startOf('day')` corrects it to `2025-10-27T00:00:00+00:00`.

One near-miss worth recording: the first version of the component test used `it` and `afterEach`, which this file does not import. The suite reported 12 pass, 0 fail while the new test never ran at all, erroring at module scope. A green run is not evidence a new test executed.
