# Development Log - 2026-10-22

## Changes

- **[drag]**: An all-day event dropped on a time slot now starts at the slot wherever its bar was grabbed and lasts one hour; before, the start depended on the horizontal grab point (read as minutes) and the length stayed 24 h. FullCalendar `EventDragging.ts:447-460`, `event-mutation.ts:131-134`, `defaultTimedEventDuration` (`options.ts:486`, `allDayMaintainDuration` false at `options.ts:511`), v7.1.1. The one hour is fixed, not a prop.
- **[drag]**: A timed event dropped on the all-day row now ends at the next midnight (RFC 5545 3.6.1, `defaultAllDayEventDuration` `options.ts:487`); before, the end was start plus the old length (e.g. 00:30).
- **[drag]**: A move keeps the event's wall-clock length: the end is the new start's clock plus the old clock length, anchored in the zone like the start. Across a clock change the event no longer grows or shrinks an hour, `delta` equals `endDelta`, and the drag mirror's end label matches the committed end. FullCalendar applies one delta to both edges (`event-mutation.ts:110-114`, `marker.ts:48-58`). A moved multi-day all-day event keeps its whole days the same way.
- **[fetch]**: A fetch in flight when `events` becomes an array (or `resources` stops being a function) no longer lands on the array. When the fetcher goes away the hook runs the unmount teardown (bump the request id, abort, clear `inFlight`, forget the fetched range and the attempt, `loading` false), shared by both paths. Switching back to a function fetches afresh.
- **[fetch]**: A failed first `resources` fetch is no longer retried by plain navigation. `mustFetchRange` takes `hasAttempted`; range-independent data is tried once, then only `refetchResources()` (or navigation with `refetchResourcesOnNavigate`) fetches. Events keep their documented retry of a failed range on navigation. The unit test that pinned `followsRange:false, fetched:undefined` to `true` now says "never tried" and has a "tried and failed" counterpart.
- **[e2e]**: `removeSettings` helper; specs "a fetch in flight when events becomes an array does not overwrite the array" and "a failed first fetch is not retried by navigating" (both orientations).
- **[fix]**: iCal export folds content lines longer than 75 octets with CRLF + one space, never splitting a UTF-8 character (RFC 5545 §3.1). One `foldLine` helper, applied once when `exportToICalendar` joins the lines.
- **[fix]**: The exported file ends with CRLF after `END:VCALENDAR` (§3.4). The old unit test only checked that `\r\n` appeared; it now pins the exact ending.
- **[fix]**: An all-day series exports `UNTIL` as a DATE (`UNTIL=20250330`), the same calendar day `formatDate` gives the series' other dates (§3.3.10: UNTIL has the value type of DTSTART). `RRule.toString()` always writes a Date `until` as a UTC DATE-TIME, so the recurrence plugin leaves it out of the options and appends it.
- **[fix]**: An all-day series exports `EXDATE;VALUE=DATE:` and `RECURRENCE-ID;VALUE=DATE:` (§3.8.5.1, §3.8.4.4); the value type otherwise defaults to DATE-TIME while DTSTART is a DATE.
- **[docs]**: `docs/export-ical.md` and the website export page no longer claim "RFC 5545 compliant" or "any compliant calendar application". They state the known limit: a recurring series in a configured `timezone` exports as UTC `DTSTART` + `RRULE`, no `TZID`/`VTIMEZONE`, so importers drift an hour after a clock change (§3.8.5.3). The fix is deferred to 4.x (roadmap 4.3.9; `docs/migration-v4.md` notes the output change). Also fixed the documented filename (`ilamy-calendar-YYYY-MM-DD.ics`, what `use-export-calendar.ts` writes) and the stale source paths.
- **[test]**: New `apps/e2e/tests/ical-export.spec.ts` with an `ical-export` scenario, and a `hideExportButton` harness parameter.
- **[decision]**: The exporter does not guard against `COUNT` and `UNTIL` together in one RRULE (§3.3.10 "MUST NOT occur in the same recur"). That comes from the stored rule, which the recurrence fix corrects at the source; a guard here would hide the source bug and any spec that checks it.
- **[week view]**: The week number now counts the first drawn day of the week, not the current date, in the week header and both resource week vertical headers (`getDrawnWeekNumber`). One grid no longer shows two numbers (Sunday-first ISO, Monday-first local, year end 52 vs 53) and it agrees with the month row. FullCalendar `TimeGridWeekNumber.tsx:44-50`.

## Notes

Resize and drag-to-create snap an edge to a slot boundary (an exact slot length) and so have no length to keep; the recurrence plugin's `add(duration, 'millisecond')` (elapsed) is a separate question, not changed here.

FullCalendar reference: `@fullcalendar/resource` 6.1.22 refetches resources on navigation only with `refetchResourcesOnNavigate`.

Three older unit tests in `export-ical.test.ts` (all-day fixtures written as UTC midnights) already fail under `TZ=America/New_York` on `main`; unchanged here.

- Hidden days: the week number counts the first VISIBLE day, as the month row does.

- A middle day of a timed multi-day event sorts among timed events (by start) although it reads "All day".

- F7 is docs only by decision: changing month `allDay` changes `onCellClick` and the form, a 4.0 change.

- Under `TZ=America/New_York` some older tests already fail on main (fixtures are `Z` instants read in the machine zone: `getWeekDays` x7, `event-form-utils` x11, `droppable-cell` x2, `use-calendar-engine` x5, `dnd-utils` x9, one business-hours form test). The new tests pass under both `TZ=UTC` and `TZ=America/New_York`.

- Not changed: the events layers' `days.at(-1).add(1, gridType)` range end is an hour off when the last column is itself a change day; it only reaches the drag segment clamp, the now line and the preview range inside that last hour. No visible repro, left for a follow-up.

- Start equal to end on one day is still allowed by the time handlers (zero-length); RFC 5545 asks for a later end.

The a11y spec asserts roles and accessible names, not an axe scan (axe is not a dependency). jsdom-style name computation (dom-accessibility-api) does not include an element's own text when it labels itself, so the date value is referenced through its own `<span id>` rather than a self-reference.

- Three existing unit tests pinned the old first-occurrence contract (a dead series row left behind); they were changed deliberately, with a comment saying why.

- Not fixed, found while sweeping (read from the code, not reproduced in the browser, so unverified): an edit with scope "this" that changes rule fields (`rrule`) ignores them (the override is stored with `rrule: undefined`); and "following" keeps the exdate of a moved occurrence that was dropped with the cascade, leaving a hole in the new series; both predate this change. (The third candidate, exdates left at the old time by a time change, was verified and fixed, see above.)

- The cut still reads the day boundary through dayjs (`dayjs.ts` is untouched); unit tests compute their expected UNTIL the same way, so they hold on any machine zone, and the New York case is an e2e spec.
