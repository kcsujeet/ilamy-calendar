# Development Log - 2026-09-11

## Changes

- **[week view]**: Merged #260 (closes #259), which stops week and day views disabling days that belong to the neighbouring month. `GridCell` now gates the padding check on `view === 'month'` rather than comparing every cell's month against `currentDate`, so a week spanning 31 March to 6 April is interactive on both sides. The month grid keeps greying its own padding.

- **[week view tests]**: Pinned the zone in the cross-month week tests and switched their cell lookups to absolute date literals. They resolved ids by formatting a UTC fixture through the machine clock, so west of UTC `2025-03-31T00:00:00.000Z` read as Sunday 30 March, the rendered week fell wholly inside March, and the scenario under test stopped existing. Measured before the fix: UTC and Asia/Tokyo passed, America/New_York and Pacific/Midway failed 4 of 4. After: all five zones pass, adding Pacific/Kiritimati.

- **[review]**: Declined the `outsidePeriodBehavior` proposal that #260 originally carried (a `disabled` / `interactive` / `navigate` enum, a per-view default, and a `classesOverride` key). Neither reference implementation has the concept.

- **[calendar/initialDate]**: Took over #266. The date a calendar opens on is now resolved by the rule the configured constructor already applies, instead of treating every input as a wall clock. A string with no offset names a clock reading, so the calendar's zone anchors it and `'2025-03-10'` opens on 10 March wherever it is read; a `Date`, a `Dayjs` or an offset-carrying string already names an instant, so only the clock it renders against changes. Before this, `initialDate='2025-03-10T22:00:00.000Z'` with `timezone="Pacific/Kiritimati"` opened on the 10th from a UTC or New York machine and the 11th from Tokyo, when the instant is the 11th in Kiritimati in all three.

- **[utils/dayjs]**: Extracted the wall-clock-versus-instant test out of `timezoneAwareDayjs` as the exported `isWallClockReading`. The rule now has one definition and two callers: the constructor, which reads the module default zone, and the engine, which has the zone in hand before `setDefault` has run.

- **[calendar/engine]**: `IlamyCalendar` hands the engine the raw `initialDate` rather than a `safeDate` result, because parsing flattens away the distinction the rule turns on. `anchorInitialDate` runs once per mount via `useState` rather than on every render; the navigation slice reads it only in its lazy initializer, so later calls were discarded.

- **[docs]**: `docs/timezones.md`, `safeDate`'s doc comment and the navigation slice's comment all described the navigation slice as the place `initialDate` gets anchored. It is the engine now.

- **[renderEvent]**: Took over #264. `renderEvent` now receives a second argument saying which slice of the event the current bar is drawing, so a renderer can square a cut edge and round a real one. An event longer than the row or day column it starts in is drawn as one bar per row and `renderEvent` runs once per bar, but until now every call looked identical, so a custom renderer had no way to tell a resumed bar from a whole one.

- **[renderEvent naming]**: Renamed the segment's fields to `isStart` and `isEnd`, matching FullCalendar's event render hook, where they are defined as the segment's range matching the event's own range (`packages/preact/src/component-util/event-rendering.ts`). The proposed names described the cut rather than the event, so every caller had to invert them at the point of use.

- **[layout/vertical]**: Day and week columns now report truncation too. `computeTopHeight` already clamped an event that started before the visible hours or ran past them; it now says which clamp it applied, so `VerticalPositionedEvent` carries `isTruncatedStart` / `isTruncatedEnd` the way the horizontal layout already did. Before this, an overnight event in a 09:00-17:00 grid reported both edges as real on both of its bars.

- **[week/day appearance]**: The default event bar reads the same two flags, so the vertical fix changes what ships without a custom renderer: an overnight bar in week or day view now squares the edge where it is cut and keeps the continuation stripe, instead of rounding all four corners as if it were a whole event. Month view already looked like this.

- **[layout/geometry]**: Dropped `spanUnits` from `PositionedEvent` and from `DraggableEvent`'s props. It was a rendering measurement, not part of the segment contract, and no renderer read it.

- **[dnd tests]**: Folded the standalone SSR test into `calendar-dnd-context.test.tsx` as a `Server Rendering` block, per the rule against new test files. Tightened it while moving it: the fixture date is a full ISO string rather than `'2025-03-31'`, the zone is pinned to UTC so the event lands in the rendered week wherever the suite runs, the count assertion is `toHaveLength(1)` instead of `toBeGreaterThan(0)`, and the third render is gone since two consecutive renders are what two successive requests do.

- **[test harnesses]**: Closed #270. The built-in view harnesses mounted a view without telling the provider, so unless a test passed `initialView` the context's `view` stayed at its default of `'month'` while a week or day grid rendered. Each harness now reads the active view and refuses to render when it disagrees, naming the prop to add. Adding the guard failed 138 tests across 8 suites, which is how many were exercising a configuration they did not ask for; all 8 now pass `initialView` and the whole suite is green again at 924.

- **[header animations]**: Header labels animated on every navigation, whether or not they had anything to show. The animation is a CSS `animate-in` that replays when its node remounts, and every header cell was keyed by `day.toISOString()`, so moving a month replaced all seven weekday cells and faded "Mon" back in over "Mon". Measured through the real header's Next button: month weekday text went `"Sun" -> "Sun"` with the node replaced. Headers are now keyed by what they render, so the fade plays on first mount and thereafter only where the text actually changed.

- **[header animations]**: In the week and resource headers the weekday and the number were animated as one unit, so a column re-introduced "Sun" alongside a number that had genuinely moved. `AnimatedDayLabel` now animates each half against its own text, so the fade plays on whichever half changed. Which half that is depends on the header, and the first attempt got it backwards: a week column keeps its weekday and moves its number (`"Sun2" -> "Sun9"`), while a month column does the reverse, because the first column is day 1 of every month and the weekday under it moves (`"Sat1" -> "Tue1"`). Freezing the weekday everywhere left both resource month headers with no animation at all.

- **[header animations]**: The week number in the corner cell was not animated at all, and the resource month vertical gutter used a plain `DayLabel`. Both now follow the same rule as the day numbers beside them.

- **[e2e]**: Started a browser test harness. Nothing here drove a real browser: the unit suite renders into happy-dom, which has no layout, so an element can be asserted present, correct and invisible at the same time, and every visual regression so far has been found by a person looking at the screen. `apps/e2e` is a Vite app that takes its whole configuration from the URL, so a test or an agent reaches any state by navigating rather than clicking through setup. Design in `docs/e2e-testing.md`.

- **[e2e determinism]**: The clock, zone, locale, viewport and colour scheme are all pinned, because a calendar renders almost everything from "today" and a suite that inherits any of them asserts something different tomorrow. Proved rather than assumed: removing `page.clock.install` fails two of the three determinism tests, and the suite passes under UTC, Asia/Tokyo, America/New_York, Pacific/Midway and Pacific/Kiritimati — the two zones that broke the week tests in #268 included. Confirmed visually too: in day view the red now-indicator sits at exactly 09:00, which is the pinned instant reaching the render path rather than just `new Date()`.

- **[e2e configuration]**: A fixture supplies the events; every calendar setting is a query parameter (`slot`, `dayMaxEvents`, `eventHeight`, `hiddenDays`, `height`, `firstDayOfWeek`, `granularity`, `timeFormat`, and the rest). There are far more combinations of settings than anyone would write fixtures for, so none are written. Every parameter validates and raises rather than falling back, because a silent default would make a test look like it covered a setting it never applied — the same failure as the view harnesses in #270.

- **[e2e coverage]**: Filled in the matrix. All 12 rendering surfaces are asserted to reach the screen (day/week/month/year/agenda, plus day/week/month in both resource orientations), then 14 behaviour specs cover what each fixture is for: overflow past `dayMaxEvents`, an event drawn as one bar per month row, an overnight event cut per day column, all-day events in their own row, `hiddenDays`, slot duration, overlapping events, and navigation. Plugins install from the URL, since `view=agenda` renders nothing without the plugin that adds it.

- **[e2e drag]**: Drag and drop is in the gate after all. `@dnd-kit` needs a real pointer sequence, so the helper presses, moves in eight steps past the activation distance, then releases. Ten consecutive runs passed, so it stays; if it ever starts flaking it comes out rather than being retried until green.

- **[e2e visual]**: Dropped before it shipped. A pixel baseline cannot tell a broken layout from an intentional restyle, so every deliberate change means opening each diff and confirming it; on a one-maintainer repo a dozen diffs per restyle gets rubber-stamped, and a check nobody reads is worse than none. Two things weaken it here specifically: the package ships no CSS, so a baseline records the harness's own theme rather than what a consumer sees, and baselines only match the platform that made them, so accepting a change needs the CI container running first. Layout is asserted through exact counts instead, which fail with a readable message. Reasoning recorded in the spec; revisit if a purely visual regression ever ships unnoticed.

One clean install resolved both. Net effect on the lockfile is 349 insertions against 927 deletions, mostly duplicate entries going away.

- **[docs]**: Audited every PR merged since v2.0.3 against the documentation before cutting the release. Coverage was better than expected — all 45 public props documented and matching the type, 38 of 41 exports mentioned somewhere — so the gaps were specific rather than systemic.

Major rather than the minor first planned: the change alters how existing consumer data renders with no action on their part, and `CellInfo.end` returns a different value, so `^2.0.3` would have delivered it silently.

- **[docs/tone]**: The v3 migration guide overstated the breaking change, and the maintainer caught it. It listed all-day events as affected, which reads as "your all-day events will break". They will not. Confirmed the v2 form wrote `23:59` (`buildEndDateTime` before #250), so events created through it are untouched.

- **[docs/tone]**: The real scope is narrower than the guide implied: only an `end` at exactly midnight changes, and that shape mostly comes from events a consumer built themselves. The guide, the changelog and the `CalendarEvent` callout now say that, with a note up front that existing events are not migrated and do not need to be.

## Notes

The `initialDate` rule matches FullCalendar's `timeZone` rule, which the docs state as: a string without an offset is "parsed (and thus displayed) as if it were" in the configured zone, one with an offset is "appropriately shifted to display" in it. Verified against https://fullcalendar.io/docs/timeZone rather than from memory.

That test is load-bearing: with the old wall-clock-for-everything branch restored it fails with `Expected "2025-03-11", Received "2025-03-10"`. The timezone block passes under UTC, Asia/Tokyo, America/New_York, Pacific/Midway and Pacific/Kiritimati.

Worth knowing for the next change here: `anchorInitialDate` takes the zone as an argument specifically because `dayjs.tz.setDefault` runs in an effect, so the module default is empty during the first render. Anything else that needs the zone during render has the same constraint.

FullCalendar exposes `showNonCurrentDates` (a boolean for whether adjacent-month days render at all) and an `isOther` flag on its day-cell render hook, and nothing resembling a behaviour mode. Google Calendar publishes nothing on the subject.

Worth following up separately: FullCalendar keeps `isDisabled` and `isOther` deliberately distinct, computing `isOther` as `!isDisabled && …` (`packages/preact/src/component-util/date-rendering.ts`), so an out-of-month day is never disabled *for being* out of month. Our month grid disables its padding, which means the deviation from the reference is our current default rather than the rejected feature. That is a behaviour change with a visible result, so it wants its own issue rather than being folded into a bugfix.

The harness mismatch the merged PR worked around is still there: `WeekView` mounts `<ViewRenderer view={weekView} />` while the provider's `view` defaults to `'month'` unless a test passes `initialView`. #260 papers over it by passing `initialView="week"` in `renderWeekView`. Anything else reading the active view from context inside a view test will hit the same trap.

#264's vertical fix is load-bearing: with the forwarding removed, the overnight test fails, both bars claiming a real start and a real end. The type-level test was checked in both directions — deleting its `@ts-expect-error` raises TS2322, and widening the contract to accept a third argument makes the directive itself unused (TS2578), so it cannot silently stop testing anything.

`renderEvent` gaining a required second parameter is not a breaking change for consumers: a function that ignores an argument still satisfies the type, so every existing one-parameter renderer keeps compiling.

The folded SSR test is still load-bearing: removing `id={dndContextId}` from `DndContext` fails it on the second render's ids, which is the regression #262 fixed. Test count is unchanged at 924, across one file fewer.

The harness guard is load-bearing, but the first attempt to prove it was not: a `sed` that silently failed to match left `initialView` in place, and the suite passed. Removing the prop properly raises `<DayView /> was mounted while the calendar's active view is 'month'`. Worth remembering that a revert experiment which changes nothing looks exactly like a fix that is not load-bearing.

The header cells are keyed by position rather than by date on purpose. They are slots, not identities: the second column of a week header is Monday's whatever week is shown, and the thing that varies inside it is keyed separately. The usual objection to index keys does not apply because the list is fixed-length and never reordered.

First attempt to measure this was wrong and worth remembering: rerendering with a different `initialDate` changes nothing, because `initialDate` is read once per mount (the `useState` from #266). Navigation has to go through the header's Next button, which is also the only way to reproduce what a user sees.

The lesson from the resource month headers: "animate the number, freeze the weekday" was a rule derived from one view and applied to five. Measuring the month header would have shown `"Sat1" -> "Tue1"` immediately. The rule that survives contact with every header is the weaker one — animate whatever changed — and it needs no per-view knowledge.

The e2e package deliberately has no `test` script. `bun run test` fans out with `--filter '*' --if-present test`, so naming it that would have pulled Playwright into the unit run; it is `e2e` instead, and the unit suite is untouched at 929 across 46 files.

Three things found by rendering the combinations and looking at them, none of which a DOM assertion would have shown:

- Screenshots taken at 500ms catch the header `fade-in` mid-flight and come out washed out. The visual layer will need `animations: 'disabled'` or the baselines will be flaky.
- Time grids open at midnight, so events at 09:30 sit below the fold and a naive baseline would record an empty grid and pass forever. Fixtures now pin `scrollTime`.
- Year view has no resource form, which matches `year.tsx` having no `orientation` branch: the Year button disappears entirely when resources are present.

Two type assumptions were wrong and the compiler caught both: `WeekDays` is a union of names (`'monday'`), not numbers, and `TimeFormat` is `'12-hour'`/`'24-hour'`, not `'12'`/`'24'`.

A drag cannot be asserted from the month DOM: the bars are drawn in an overlay positioned over the cells rather than inside them, so "is this event in Thursday's cell" has no element to ask. The harness holds the events and publishes what `onEventUpdate` hands back, which is both easier to assert and closer to what a consumer actually depends on. Both drag tests are needed together — the disabled case alone would pass even if dragging never worked at all.

Page objects locate a resource by its title rather than by testid. The axis header carries `horizontal-row-label-*` when resources are rows, `resource-columns-header` when they are columns, and nothing at all in the vertical week header; the title is the only thing present in all three, and it is what a person reads.

The E2E job runs on `ubuntu-latest`, not in the Playwright container. The container was chosen for identical font rendering when baselines were still planned; with those gone its only remaining effect was breaking `setup-bun`, which needs `unzip` and the image does not ship one. Caught by CI on the first run, not locally — a reminder that a CI job is itself untested until it has run.

Astro 7 renders markdown with Sätteri by default and demotes `@astrojs/markdown-remark` to an optional peer, so MDX stopped building until it was added as a direct dependency. The error says so plainly, which is more than most upgrades manage.

The build failed for a while against a version that was already installed correctly: `apps/website/node_modules/astro` still held a nested 6.4.6 while the root had 7.2.10, so the site resolved the old copy and the error pointed at a missing export that the new one has. Worth knowing when a dependency error contradicts what the lockfile says: check for a nested copy before doubting the version.

Reachability was checked before treating this as urgent, and the answer was that it is not. The site is a static build with no adapter, deployed as files to Cloudflare Pages, with no `<Image />` or `getImage` anywhere and no raster images at all. The advisory needs a server optimizing an untrusted AVIF, and there is no server. Upgraded as maintenance rather than as an incident.

The report itself had three errors worth noting, since it was machine-generated: it cited `bun.lock:1047`, which is `acorn-jsx` (astro is 1073); it quoted the pin as `6.4.6` rather than `^6.4.6`; and its fallback mitigation was to override `sharp`, when GitHub lists the vulnerable package as `astro` with the fix in 7.2.8.

Two process lessons from this one, both worth more than the fix.

`pkill -f "astro dev"` does not kill the dev server: the process is `node .../astro.mjs dev`, so the pattern never matches. Five servers accumulated on 4200 through 4204 while every measurement went to 4200, which was the first one, started before any change. That produced a confident claim that two `vite` config options were load-bearing, complete with a revert test that appeared to prove it. Both claims were wrong; removing both options leaves the page clean. Astro 7 ships `astro dev stop` / `status` / `logs` for this, and `lsof` shows strays.

A revert test only means something if the thing being probed actually reloaded. Mine had not, twice, and the failure mode looked exactly like success.

Regenerating the lockfile moved Biome from 2.4.16 to 2.5.13 inside the existing `^2.4.16` range, and the newer version flags five things the old one did not. Three are `noUnsafeOptionalChaining` in the recurrence editor tests, and the rule is right: `(preset?.byweekday as T[]).map(...)` is not guarded by the `?.` at all, because the cast puts a member call after it, so an undefined preset would throw a TypeError rather than fail an assertion. Defaulting to `[]` keeps the expectation exact. The other two are SVGs without a `<title>`.

Worth noting how close this came to shipping broken: `bun run check:fix` was run with its output discarded and its exit code unchecked, so "lint clean" was reported when the repo did not lint. The commit hook caught it. Check exit codes, not just absence of output.

The release is v3, not the minor that was first planned. The exclusive `end` changes how existing consumer data renders with no action on their part, and it changes a return value — `CellInfo.end` from `onCellClick` is the next midnight now, not `23:59`. On `^2.0.3` that would have arrived automatically. The repo's own rules frame the inclusive `end` as a deviation, so it is a bug fix by intent, but semver keys off effect on consumers rather than intent.

The first draft of the `PluginMutationResult` entry was written from inference and was wrong: it described a plugin "claiming" a mutation or declining it. The real type carries `events` plus `updated`/`added`/`deleted`, which is how one scoped recurrence edit becomes several persistence operations. Checked against `packages/types/src/index.ts` before committing, which is the only reason it is not now a documented fiction.

Worth remembering when writing a migration guide: accurate and alarming are different failures. Every sentence in the first draft was defensible, but the affected/not-affected table used a bold "Yes" for all-day events, and a reader scanning only that table would conclude their data was about to break. The fix was to measure what actually changes and let the table say so.
