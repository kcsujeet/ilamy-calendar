# Development Log - 2026-08-28

## Changes

- **[drag-and-drop]**: Fixed a drop onto a different resource doing nothing for a cross-resource event (one with `resourceIds`). `getUpdatedEvent` wrote only `updates.resourceId`, but `getEventResourceIds` ignores `resourceId` whenever `resourceIds` is present, so the time moved and the resource silently did not. Now follows FullCalendar's resource mutation: remove the row the drag started from, add the drop target, dedupe, and leave an event that was not in the source row untouched. Required threading the rendering row's id into the drag payload as `sourceResourceId` (a cross-resource event is rendered once per resource, so the drop had no way to know which row it came from).
- **[docs]**: Added a hard rule to `AGENTS.md` — behavior must follow RFC 5545, and where the RFC is silent it must match FullCalendar/Google Calendar, cited. Inventing semantics is a bug even when self-consistent and green.

- **[recurrence]**: Fixed a moved "this event" override rendering twice in the cell it was dropped on. The override had two emitters: `generateRecurringEvents` merged it into the series expansion (`{...event, ...existingOverride}`), and the plugin's `transformEvents` also passed the stored override row through untouched. The EXDATE filter used to hide the merged copy by accident — it compared the *emitted* event's start against `exdates`, which hold the ORIGINAL occurrence ISO. That matched only while the override sat at its original time, so a title-only edit looked fine and a drag produced a duplicate.
- **[recurrence]**: `generateRecurringEvents` now SKIPS an occurrence that has an override (rather than emitting a merged copy of it), and keys its EXDATE check off the occurrence instead of the emitted start. `transformEvents` became the single emitter of overrides, merging each over its base so a sparse imported VEVENT still inherits the fields it omits (`rrule` forced off).

## Notes

- `provider.test.tsx`'s "should not create duplicate events when recurring events are modified" was asserting `'2'` on a fixture that is exactly the reported bug (base + EXDATE + a moved modified instance). The test name was right; the assertion had been fitted to the buggy output. Now `'1'`.
- Both halves of the fix were verified load-bearing by reverting each and watching tests fail (skip -> 2 failures, merge -> 1 failure).
- `updateThisScope` still writes an EXDATE *and* an override for the same occurrence. That EXDATE is now redundant for rendering (the skip covers it) but is still what `deleteRecurringEvent` relies on once the override is removed, so it stays.
- Side effect, an improvement: an override moved outside the expansion window now still renders. Previously only the merged copy was range-correct and the occurrence had to fall inside `rule.between`.
- The cross-resource drop semantics were taken from FullCalendar's source, not invented. RFC 5545 is silent here: its `RESOURCES` property (3.8.1.10) is a free-text equipment list with no resource-axis or drag concept. FullCalendar's docs do not specify it either, so the rule came from `premium/packages/preact-scheduler/src/resource/EventDragging.ts` (`massageEventDragMutation` + `applyEventDefMutation`).
- One deliberate divergence from FullCalendar: it requires BOTH a source and a target resource before mutating at all, so an event dragged from a context with no resource axis never changes rows. ilamy keeps "a single-resource event takes the target" in that case, because `all-events-dialog.tsx` renders draggables with no resource and that behavior was already pinned by `dnd-utils.test.tsx`. Where a source row exists the two agree exactly.
- Docs sweep found a pre-existing error unrelated to these fixes: the website's recurrence page showed `exdates` as `Date` objects (`dayjs(...).toDate()`), but the field is `exdates?: string[]` and the filter does a string `includes` on ISO — a `Date` there never matches, silently. Corrected to `.toISOString()`. `docs/types-and-interfaces.md` and `docs/testing-guide.md` already had it right.
- Neither resource doc previously stated what a drop does to `resourceIds`, because it never did anything. Both now document the swap rule and cite FullCalendar.
