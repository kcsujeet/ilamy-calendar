# 3.3.8 Async events Implementation Plan

> TDD (superpowers:test-driven-development). Part of `docs/roadmap.md`, release 3.3 (formerly 3.4.1).

**Goal:** `events` can be a function the calendar calls with the visible range, so consumers load events on demand,
with a loading signal, cancellation of superseded fetches, and error reporting. An array keeps working exactly as today.

## The standard (FullCalendar v7.1.1 source, `packages/preact/src/`)
- Function source `(info) => Promise<EventInput[]>` (or callbacks); `info` = `{ start, end, startStr, endStr, timeZone }`,
  end exclusive (`event-sources/func-event-source.ts:7-21`; https://fullcalendar.io/docs/events-function).
- The requested range is the view's active range — for month this includes the leading/trailing other-month days of the
  grid (`reducers/eventSources.ts:13,29`; `daygrid/TableDateProfileGenerator.ts:6-57`).
- `lazyFetching` (default true): refetch when never fetched, when a fetch is in flight, or when the active range is not
  inside the last fetched range; a time zone change forces a refetch (`reducers/eventSources.ts:70-80,125-134`).
- Superseded fetches: each fetch gets an id; a response whose id is not the latest is ignored
  (`reducers/eventSources.ts:161,216-241`).
- `loading(isLoading)` fires on transitions of "any fetch in flight" (`CalendarDataManager.ts:322-328,709-717`).
- Failure: failure callback runs; shown events are KEPT; the fetched range is not recorded, so the next navigation
  retries (`reducers/eventSources.ts:189-205,58-60`).
- `refetchEvents()` refetches regardless of lazyFetching; old events stay visible until the new ones replace them
  (`api/CalendarApiImpl.ts:509-511`, `reducers/eventStore.ts:114-117`).

## Decisions (record in TSDoc + docs; justify deviations)
```ts
export interface EventsFetchInfo {
	start: Dayjs        // inclusive, calendar zone
	end: Dayjs          // exclusive
	startStr: string    // ISO
	endStr: string      // ISO
	timezone?: string
}
export type EventsFetcher = (info: EventsFetchInfo, options: { signal: AbortSignal }) => Promise<IlamyCalendarPropEvent[]>
// IlamyCalendarProps
events?: IlamyCalendarPropEvent[] | EventsFetcher
lazyFetching?: boolean               // default true
loading?: (isLoading: boolean) => void
onEventsError?: (error: unknown) => void
```
- Range = the full visible grid (month includes padding days), end exclusive; in a resource or custom view, its visible range.
- Superseded fetch: ABORT it through the `AbortSignal` (beyond the convention, which only ignores it) and also ignore any
  late result (a consumer may not honour the signal).
- `loading` fires only on transitions; an array never triggers it.
- On failure keep shown events, call `onEventsError` (if absent, `console.error` once per failure), don't record the range.
- Mutations with a fetcher: the store applies user mutations optimistically and reports them through the existing
  callbacks; the next fetch (navigation, `refetchEvents`, zone change) replaces the store with exactly what the fetcher
  returns. Deviation: the convention keeps source-less client-added events across a refetch; ilamy has one source, so
  that would duplicate events the server now returns — record it.
- Expose `refetchEvents()` on the context API now (the `ref` API, next feature, will surface it too).
- A changed fetcher function identity (consumer recreates it each render) must NOT refetch on every render: document
  that the fetcher should be stable (`useCallback`) and refetch only on range/zone change or `refetchEvents()`. Decide
  and justify whether identity change triggers a refetch (prefer: yes, it's how consumers express "my query changed" —
  but then guard the common inline-function case: check how the repo's `useLatestHandler` pattern applies and pick the
  simplest correct rule; record the choice).
- Out of scope (record cuts): multiple `eventSources`, `startParam`/JSON-feed URLs (a feed plugin is roadmap 4.3.9).

## Where (verify): `features/calendar/hooks/calendar-data/use-event-store.ts` (today: resets from the `events` prop),
`use-calendar-data.ts`, the visible range the engine already computes (`currentRange` / `getCurrentViewRange`), the
provider/context/types, `docs/hooks-and-context.md`. Harness: an e2e scenario/param whose fetcher resolves after a
configurable delay and can be made to fail (`&fetch=delayed&fetchDelay=300`, `&fetch=failing`) and that publishes each
fetch's range and abort status so specs can assert them.

## Tests first
Unit (hook level, fake fetcher): first render fetches the visible range (month includes padding days); navigating inside
the fetched range doesn't refetch with lazyFetching, does with `lazyFetching={false}`; a second navigation while the
first fetch is pending aborts the first and its late result is ignored; `loading` true→false once per fetch cycle;
failure keeps events + calls onEventsError, next navigation retries; `refetchEvents` refetches and keeps events visible
until resolved; timezone change refetches; an array `events` prop behaves exactly as before (all existing tests green).
e2e: delayed fetcher shows events after the delay; rapid next-next-next shows only the final range's events and the
published fetch log shows the earlier ones aborted; failing fetcher keeps the previous events and shows no crash; a drag
under a fetcher reports the change and survives until the next refetch.

## Global constraints
No breaking change (array `events` identical); configured dayjs only; ISO strings in tests; no `!`, no `any`, `.at()`,
named exports, name every condition; unit AND e2e first; revert proof; machine-zone-independent new tests; docs
(`docs/hooks-and-context.md`, `docs/types-and-interfaces.md`, website props page + a "Loading events" section,
`docs/api-parity-checklist.md` tick events-as-function and loading, roadmap row). Public text never frames this as
parity; cite behaviour with file:line. No dev log, no CHANGELOG.
