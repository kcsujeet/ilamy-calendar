# Development Log - 2026-10-08

## Changes

- **[vertical day grids, #322]** All-day events were never drawn in the vertical resource month view, nor in the vertical resource week view at daily granularity. Both are vertical grids whose rows are whole days (`gridType: 'day'`), and both have no all-day row (`view-renderer.tsx` builds one only for hour grids). Yet `useProcessedDayEvents` and `layoutVertical` each dropped every all-day event, on the assumption that an all-day row would draw them. Now `layoutVertical` alone decides: a time grid (hour or minute rows) leaves all-day events to its all-day row, as FullCalendar's time grid does (`AllDaySplitter`, `timegrid/src/DayTimeColsView.tsx:27`, v6.1.21), and a day grid draws them like any other event, as FullCalendar's day grid does (`daygrid/src/DayTable.tsx` has no all-day split, v6.1.21). The hook's duplicate filter is gone. The existing day-grid placement was already right: measured in the browser, the bar runs from its first day's row to where its exclusive end's row starts.
- **[drag, all-day kind]** Found while pinning the above, and already on `main`: dragging an all-day event within a month or resource day grid turned it into a timed event. Those cells report `allDay: false` with no hour (`GridCell`'s default), and `calculateDropTimes` read `false` as "a timed-only cell". It now follows FullCalendar: a drop changes an event's kind only when it crosses between an all-day area and a timed one (`interaction/src/interactions/EventDragging.ts:450`, v6.1.21). A time slot makes it timed, an all-day cell makes it all-day, and a whole-day cell keeps the event's own kind. A timed event dropped on a month cell still keeps its clock.
- **[drag mirror]** Found while testing the demo: dragging an all-day event on a vertical day grid showed a time range on the mirror ("12:00am – 12:00am"), since no all-day event had reached that mirror before. `VerticalDragPreview` now prints the time only for a timed event, per FullCalendar: "Events that are all-day will never display time text anyhow" (https://fullcalendar.io/docs/displayEventTime). The resting bars already showed no time.
- **[e2e harness]** `event-state` now publishes each event's `allDay`, so a spec can tell an all-day drop from a timed one at midnight. That gap is why the drag bug went unnoticed.

## Changes (#321 follow-up: review findings)

PR #321 (reapply scrolling when rendered hours change, closing #320) was merged with its review findings outstanding; this branch fixes all of them.

- **[scrolling]** The scroll key repeated the visible hours once per resource row (horizontal) or per resource column (vertical), so adding, removing or filtering a resource scrolled a reader back to `scrollTime`/now with unchanged hours. Both grids now call one helper, `getScrollKey(view, currentDate, columns)` in `features/calendar/utils/scroll-key.ts`, which keys on the distinct hours on screen. It reads a column's grouped `days` or its single `day` alike (the two grids used to read them differently). Both grids build it on every render (round 1 removed a horizontal-only guard; see below). The comment explaining which grids scroll is back above the hook call it describes.
- **[docs]** The FullCalendar standard behind the hours trigger is now cited, on `getScrollKey`: its time grid rescrolls when its date profile, which carries the slot range, changes (`timegrid/src/TimeCols.tsx:136`, `core/src/DateProfileGenerator.ts:164,167`, v6.1.21). The website props table says adding a resource with the same hours does not count. The `scrollTime` JSDoc in `types/index.ts` is left as #321 wrote it: any edit there changes the fingerprint of a long-standing clone between that file and `calendar-provider.tsx`, and Fallow's new-only gate then reports it as new.
- **[tests]** The #320 tests could not tell scrolling to now from falling back to `scrollTime` (both were 09:00) and only counted `scrollTo` calls. A shared fixture (`src/testing/scroll-test-fixtures.tsx`) now pins now at 09:00, uses `scrollTime` 07:00, and stubs element geometry one hour per 100px, so the unit tests assert where the scroll lands. The scaffold the two grid test files had duplicated lives there, with `buildScrollCalendar` taking an options object (no positional boolean flags, no unused `view`) and `buildBusinessHours` (was `hours`) leaving `daysOfWeek` out rather than listing a hand-written week (with no `daysOfWeek` the hours apply to every day, `business-hours.ts:151-160`). Vacuous `scrollLeft = 123` / `toBe(123)` checks (with `scrollTo` mocked they could not fail) are gone. New cases: a resource added with equal hours, a regular horizontal grid and an hour-less vertical grid never scroll, and a horizontal column's grouped `days`.
- **[e2e]** The spec now expects 09 for `scrollToNow` and 07 without it, and a new case checks that a re-render and an added resource leave a reader's scroll alone, each waited out first (`setSettings` returns before React re-renders, so the old check could read the frame before it). The harness gains a `resourceCount` query parameter (keep the scenario's first N resources) to add a resource to a mounted calendar.
- **[logs]** Merging #321 left eleven daily logs; removed 2026-09-20 and retracted #321's log line claiming it removed 2026-09-19.

## Changes (#324 review round 1)

Reviewed #324 with the gate review (ten gates plus verification); correctness, structure, datetime and i18n passed. Fixes:

- **[scrolling]** The horizontal grid builds the key unconditionally, like the vertical one. Its `isResourceCalendar ? getScrollKey(...) : ''` guard was untestable (with the hook disabled the key is never read; swapping `''` for the real key left every test green) and saved about 42 string conversions per render of a month grid. This also removes a multi-line ternary.
- **[naming]** Verb-led helper names: `getColumnHours` (was `hoursOf`), and in the fixture `getHourOfElement`, `buildRectAtHour`, `getLastScrollInHours`, `restoreScrollGeometry`; in `scroll-key.test.ts` `buildDateAtHour`, `buildHourColumn`, `buildGroupedColumn`, `getTestScrollKey` (was `at`, `hourColumn`, `groupedColumn`, `key`).
- **[tests]** The five tests both grids shared now live once, in the fixture's `testScrollingWhenHoursChange(orientation, getScrollTo)`, with `setUpScrollGeometry`, `buildScrollWeek`, `getVisibleHours` and `ScrollTestProvider`; each grid file keeps only its own cases. Expected offsets are computed from named hours (`NOW_HOUR - WIDE_START`) instead of commented magic numbers. `getScrollKey` gains a test that changes only the date (dropping the date from the key failed nothing before).
- **[e2e]** The reader-scroll spec now asserts the opening scroll exactly (aligned on 09) instead of `toBeGreaterThan(0)`, waits two animation frames before each "nothing moved" read, and names its viewport, height and scroll offset. The comment on the pinned hours sits above the value it explains.
- **[docs]** `getScrollKey`'s JSDoc is shorter but keeps the FullCalendar citation (the repo rule requires one, overriding the clarity gate's "drop it"); `scroll-key.test.ts` no longer narrates a ticket number.

Declined, with evidence: a plain `spyOn` in the fixture (measured this session: a `spyOn` on `HTMLElement.prototype` leaves an own property after `mockRestore`, and five view-test file pairs then failed by run order); trimming `buildRectAtHour`'s fields (its `DOMRect` return type requires them); building the vertical key only when scrolling is on (`vertical-grid.tsx` derives `hasRowsToScroll` from `expandAllDayRow = columns.every((c) => !c.days?.length)`, so with scrolling off no column holds an hour to convert).

Revert checks re-run on the restructured tests: no de-duplication fails 3 unit and 2 e2e tests; the hours left out of the key fails 15 unit tests; the scroll-to-now branch removed fails 2 unit and 4 e2e tests; either `enabled` gate removed fails its "never scrolls" test; the date dropped from the key fails 3 `getScrollKey` tests.
