# Development Log - 2026-09-19

## Changes

- **[drag and drop]**: Live drag preview. While an event is dragged, the grid
  paints a snapped mirror of where it would land, the cells the candidate covers
  are highlighted, and the source bar dims in place. The floating chip under the
  cursor is suppressed while that mirror is on screen. Matches FullCalendar and
  Google Calendar, which show the candidate in the grid rather than only under
  the pointer.

- **[drag and drop]**: Grab offset. Dropping an event puts the point you GRABBED
  under the pointer, instead of re-anchoring the event's start there
  ([FullCalendar moves by a delta](https://fullcalendar.io/docs/eventDrop)). The
  offset is read from where the pointer sat inside the rendered bar, measured
  against the span that bar draws.

- **[drag and drop]**: A timed event moved between day cells keeps its time of
  day and changes only its date, matching Google Calendar and FullCalendar.

- **[drag and drop] fix**: `calculateDropTimes` chose its branch on
  `data.type === 'time-cell'`, a value no component emits — `grid-cell.tsx` is
  the only `DroppableCell` call site and always passes `type="day-cell"`. Every
  hour-grid drop therefore took the day-cell path, which overwrites the dropped
  hour with the event's own clock, so dragging an event up or down a week or day
  column did not move it at all. It now branches on `data.hour !== undefined`,
  which is what actually separates an hour slot from a day cell (an hour grid
  publishes `hour` on every cell it registers; month and the all-day band do
  not). Caught in review, before this branch was committed.

- **[drag and drop] fix**: The grab offset measured the pointer fraction against
  the rendered rect but scaled it by the WHOLE event's duration. A bar the grid
  clipped (a multi-week event in a month row, an event starting before the first
  visible hour) draws only part of the event, so the two used different units and
  a mid-bar grab landed days out. The offset is now taken from the segment the
  bar draws, then expressed relative to the event's start, and clamped so
  grabbing the last pixel grabs the last slot rather than one past the event.

- **[drag and drop] fix**: The all-day band painted a mirror for a timed drag.
  Real events reach that row through `useProcessedWeekEvents({ allDay })`, which
  keeps only all-day events; the preview path bypassed it. The row now tells its
  events layer whether it is the all-day band, and the preview takes the same
  rule.

- **[claude config]**: The repo's Claude Code plugins install themselves.
  `.claude/settings.json` already declared the `kc-claude-kit` marketplace in
  `extraKnownMarketplaces` and enabled its four plugins, but enabling is not
  installing: since Claude Code v2.1.195 a plugin from an external source stays
  uninstalled until someone runs `claude plugin install`. A `SessionStart` hook
  now runs that for whatever is missing, so a fresh clone needs no manual
  `/plugin` step.

- **[drag and drop] structure**: Split the pieces this branch grew into their
  own units. `CalendarDndContext` was 183 lines doing two jobs; the drag session
  (refs, candidate placement, handlers, sensors) is now `useCalendarDrag` and
  the commit path (mutation plus the owner's scope dialog) is `useDropCommit`,
  leaving the component as wiring. `dnd-utils.ts` split along the same line:
  what a drop MEANS stays there, pointer geometry moved to
  `lib/utils/grab-offset.ts`. Each grid's events layer became a folder holding
  the layer, its bar and its mirror.

- **[drag and drop] fix**: The drop-target highlight was `bg-accent`, which is
  also the cell's own hover fill, and in the default shadcn palette `--accent`
  and the disabled mix are both `oklch(0.97 0 0)` in light mode. Hover, drop
  target and disabled were three states painted one colour, and this branch made
  it obvious by lighting up a whole range at once. The cells now carry a pale
  wash of the DRAGGED EVENT's own colour, the way Google Calendar tints a drop
  target. Hue is what does the work: a consumer theme may be monochrome (the
  demo sets `--primary` and `--foreground` to the same pure black, zero chroma),
  and there every grey tint sits on the same axis as the disabled fill, so no
  amount of lightening separates them. A neutral block behind a coloured card
  also just reads as an artifact.

- **[drag and drop] fix**: The mirror and the drop-target wash painted every
  event the same fallback blue. Both read `event.backgroundColor` only, but an
  event may carry its whole fill in `color` instead — the playground's own seed
  data does (`color: 'bg-teal-100 text-teal-800'`, no `backgroundColor`) — and
  each field accepts either a Tailwind class or a CSS value. `DefaultEventContent`
  already handled all of it by passing both fields through `cn` (twMerge lets a
  later `bg-*` win) AND setting them inline (where only a real CSS colour
  applies). That resolution now lives in one place, `lib/utils/event-colors.ts`,
  used by the bar, the mirror and the wash, so the three cannot drift again.

- **[playground]**: The seed data now covers all nine combinations an event can
  reach the renderer with (`backgroundColor` and `color`, each absent / a
  Tailwind class / a CSS value), one titled event per case. The old seed used
  exactly one of the nine, which is why a renderer that handled only
  `backgroundColor` looked correct in the demo.

## Changes (later session — drag hierarchy)

- **[drag and drop] fix**: While dragging, three surfaces were painted in the
  same hue at nearly the same strength — the mirror (`opacity-80`), the source
  bar (`opacity-40`) and a drop-target wash in the dragged event's own colour at
  `0.75`. On a pastel event none of them could be told apart, and because the
  wash is per-cell, a multi-day drag flooded every cell of the span (a Sep 8→21
  event tinted 17 cells across three week rows). The hierarchy is now the one
  FullCalendar ships:
  - **Mirror is opaque.** `.fc-event-mirror` carries no opacity rule at all;
    only the bar left behind is dimmed. `shadow-lg` plus the `border-card`
    hairline is what lifts it off the grid.
  - **Source ghosts to 0.75**, matching
    `.fc-event-dragging:not(.fc-event-selected){opacity:.75}`. At 0.4 a pastel
    fill faded to nearly nothing.
  - **The wash is gone.** `DropTargetWash` is deleted. The cell still reports
    the landing on `data-drop-target` for a consumer to style; it just paints
    nothing itself.

- **[drag and drop] refactor**: `useDragLandingHere` returned the whole
  `DragPreviewState` solely so the cell could read `event` for the wash. It is
  now `useDragLandsHere`, returning a boolean — which is all `data-drop-target`
  ever needed.

## Changes (fifth pass — corners are per-axis)

- **[drag and drop] fix**: `eventSurfaceRadius` squared the LEFT and RIGHT of
  any truncated bar, including in the week and day time grids — so a timed event
  running past the visible hours drew square left/right edges, which marks the
  wrong two sides. A time-column bar is cut along the VERTICAL axis and is
  horizontally complete inside its own column.

  The helper now takes the axis, and **only a horizontal grid squares
  anything**. That is FullCalendar's own rule, not an invention:
  `.fc-direction-ltr .fc-daygrid-block-event:not(.fc-event-start)` zeroes the
  left radii and `:not(.fc-event-end)` the right, while timegrid carries no
  corner rule at all and leaves its events fully rounded. Squaring top/bottom in
  the vertical grid was considered and rejected for the same reason — the
  standard does not do it.

  The axis is **ambient, not a prop**. It was first threaded as a required prop
  on `DraggableEvent`, which meant carrying a compile-time constant down three
  components (`DraggableEvent` → `renderEventContent` → `DefaultEventContent`)
  from four call sites. It is now `GridAxisContext`, provided by the two events
  layers — the only components that know the answer, and they know it as a
  literal.

  It cannot come from the calendar context, which was the obvious first guess:
  `view: 'week'` renders BOTH a vertical time grid and a horizontal all-day
  band, so `view` does not determine the axis. Only the layer does. The context
  defaults to `horizontal` for a bar rendered outside any grid (the all-events
  dialog), which is never truncated and so cannot be affected by the default.
