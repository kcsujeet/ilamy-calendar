# Development Log - 2026-10-12

## Changes

- **[docs]**: Added `docs/fullcalendar-parity-plan.md`, the master plan for parity with FullCalendar v7.1.1, built from a sweep of the v3.2.1 code, the FullCalendar v7 docs and all 109 issues. Shape: two additive minors (3.3 editing and time axis; 3.4 data, control, plugin-contract hooks, deprecations), the breaking 4.0 (Temporal migration, ISO dates, optional built-ins moved to plugins, removals), then 4.1 (scheduling rules, drag ecosystem), 4.2 (scheduler) and 4.3 (views, a11y, RTL, print, interop). Patches for bug fixes ship from `main` at any time.
- **[docs]**: The plan keeps the core small: a feature is a plugin when the public contract plus a small general hook can carry it. Six hooks are added in 3.4 for that.
- **[process]**: The plan's Delivery process runs the work without the owner in the loop: the main session manages Sonnet engineers (worktrees), persona QA agents and the code-review gates, and does the final verification itself. `AGENTS.md` gains a scoped exception: for the parity program the manager may commit on `parity/*` branches, push and open PRs after final verification; the owner merges. Never `main`, never local-only commits.
- **[docs]**: `docs/api-parity-checklist.md` points to the plan.
- **[investigation]**: `TZ=America/Vancouver bun test` in `packages/calendar` fails 157 tests (60 Kolkata, 76 Auckland). Not a problem in practice: `bun test` runs in UTC unless `TZ` is exported (https://bun.com/docs/test/time; measured: UTC inside `bun test` on a Vancouver machine), as does CI. Nearly all of them are tests with UTC-shaped expectations, passing once the calendar's zone is pinned to UTC. A rewrite of 31 test files to offset-less inputs was made and then reverted on the owner's call: it fixed a failure nobody runs into and broke the full-ISO-string test rule. The sweep surfaced one real bug, below.
- **[bug, not fixed: needs `packages/utils/src/dayjs.ts`]**: the one real machine-zone leak found. The published bundle carries the dayjs configuration twice (`dist/shared/chunk-nvtnncwx.js` and `chunk-bgegqhb4.js`; `dist/index.js` imports both). The calendar's own `@ilamy/utils/dayjs` import resolves to source through calendar's tsconfig `paths`; `@ilamy/ui`'s (`current-time-indicator.tsx`) resolves through the `@ilamy/utils` package exports, because `packages/ui/tsconfig.json` has no `paths`. The `fixTimezoneOffset`/`compareByInstant` patches are not idempotent, so the second copy wraps the first. Either copy alone reads correctly; both together give a start-of-week with the right instant but a clock reading an hour early when the machine's own clocks change near that date. London calendar on an Auckland machine (clocks forward 28 Sep 2025): the week of 1 October reads `2025-09-27T23:00+01:00`, `.day(1)` steps to 22 September, and the month grid repeats that week and drops 29 Sep-5 Oct. Reproduced through `dist/index.js` alone, and from source by importing `src/dayjs.ts` twice (`?second-copy`). The test environment double-loads too (source plus the `@ilamy/calendar` dist the plugin packages resolve), which is why `month.test.tsx` "across a DST transition" fails on an Auckland machine. Not fixed: the fix is the owner's call (a `dayjs.ts` change or a build change). A failing test was written and then removed on the owner's call; it lands with the fix, where it belongs (`packages/utils/src/dayjs.test.ts` for the `dayjs.ts` fix). Recorded in `docs/timezones.md`'s Temporal section: the migration removes the patches, so it fixes this; the build should still resolve `@ilamy/utils` once.
