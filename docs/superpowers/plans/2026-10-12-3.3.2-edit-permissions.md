# 3.3.2 Edit permissions Implementation Plan

> **For agentic workers:** Implement task by task with TDD (superpowers:test-driven-development).
> Part of `docs/roadmap.md`, release 3.3, item 3.3.2.

**Goal:** Consumers control, per calendar and per event, whether an event can be moved and (from 3.3.3)
resized, and can veto any candidate placement during a drag with `eventAllow`.

**Architecture:** One pure resolver `resolveEditability(event, calendarFlags)` decides `startEditable` and
`durationEditable`. Dragging reads `startEditable` to decide whether an event bar is draggable at all. The
existing refusal path (a drop cell's `disabled`, surfaced as `isDropAllowed` in the drag preview and as a
`null` result in the drop handler) gains one more condition: `eventAllow`. No new refusal mechanism.

## The standard (FullCalendar v7.1.1 source, tag `v7.1.1`, paths under `packages/preact/src/`)

- Within one level, the specific flag beats `editable`: `startEditable = startEditable ?? editable`, same for
  duration (`component-util/event-ui.ts:61-75`).
- Across levels: calendar, then source, then event; a later level wins when it is set
  (`event-rendering.ts:190-205`, `event-ui.ts:82-94`). ilamy has no event sources yet, so: calendar, then event.
- A bar is draggable iff `startEditable` (`event-rendering.ts:291-302`, `StandardEvent.tsx:78`); the resizer
  needs `durationEditable` (`StandardEvent.tsx:95-96`) — consumed by 3.3.3.
- `eventAllow(dropInfo, draggedEvent)` runs on **every hover change**, not only on drop, after constraint and
  overlap checks; `dropInfo` is the candidate range plus `allDay`; `draggedEvent` is the event **before** the
  drag. On `false`: no preview at the invalid spot, a page-wide not-allowed cursor, and no drop / no change
  callback (`validation.ts:147-174`, `EventDragging.ts:173-211`). Docs: https://fullcalendar.io/docs/eventAllow,
  https://fullcalendar.io/docs/editable, https://fullcalendar.io/docs/eventStartEditable.

## Deliberate deviation (record in TSDoc and in the roadmap's D-list)

- FullCalendar's `editable` defaults to `false` (`options.ts:495`). ilamy's drag is on by default today, so
  `editable` defaults to `true` until 4.0 (no breaking change in 3.x). Note it as a 4.0 candidate in the TSDoc.

## API

```ts
// IlamyCalendarProps (packages/calendar/src/features/calendar/types/index.ts)
/** Events can be moved (and, from 3.3.3, resized). @default true (FullCalendar defaults false; see TSDoc note) */
editable?: boolean
/** Events can be moved. @default editable */
eventStartEditable?: boolean
/** Events can be resized (used by 3.3.3). @default editable */
eventDurationEditable?: boolean
/** Veto a candidate placement while dragging. Called on every change of the hovered placement. */
eventAllow?: (dropInfo: EventDropInfo, draggedEvent: CalendarEvent) => boolean
/** @deprecated Use `editable={false}`. Kept until 4.0. */
disableDragAndDrop?: boolean

// packages/types/src/index.ts
export interface EventDropInfo {
	start: Dayjs
	end: Dayjs
	allDay: boolean
	/** The resource the event would land on, in resource views. */
	resourceId?: string | number
}
// CalendarEvent gains:
editable?: boolean
startEditable?: boolean
durationEditable?: boolean
```

Resolution (pure function, own small file in `features/calendar/utils/`, exported for its unit test):

```ts
export interface CalendarEditFlags { editable?: boolean; eventStartEditable?: boolean; eventDurationEditable?: boolean; disableDragAndDrop?: boolean }
export const resolveEditability = (event: CalendarEvent, flags: CalendarEditFlags): { startEditable: boolean; durationEditable: boolean }
```

- Calendar level: `calendarEditable = flags.editable ?? !flags.disableDragAndDrop` (an explicit `editable` wins
  over the deprecated alias). `calendarStart = flags.eventStartEditable ?? calendarEditable`; same for duration.
- Event level: `eventStart = event.startEditable ?? event.editable`; set → wins over the calendar level.

## Where it plugs in (find the exact lines; names below exist today)

- `disableDragAndDrop` flows prop → `stores/calendar-context/calendar-provider.tsx` → `calendar-context.ts` →
  `components/droppable-cell.tsx:122-157` (it disables the drop cells today). Add `editable`,
  `eventStartEditable`, `eventDurationEditable`, `eventAllow` alongside it in the same flow.
- The draggable bar (`components/draggable-event/`): disable dragging when `startEditable` is false for that
  event. With the calendar-level flag false, keep today's `disableDragAndDrop` behaviour exactly (check what it
  does to cells and bars and preserve it for the alias).
- `hooks/use-calendar-drag.ts` `getCandidatePlacement` (`isDropAllowed: !data.disabled`) and
  `components/drag-and-drop/dnd-utils.ts` (drop returns `null` when `data.disabled`): also refuse when
  `eventAllow` returns false for the candidate `{ start, end, allDay, resourceId }` and the original event.
  Evaluate it once per placement change, not per pointer move (it must be cheap for consumers).
- `eventAllow` does not apply to the event form or to drag-to-create (FullCalendar's `selectAllow` covers
  selection; that is 4.1.3).

## Tests to write first

Unit:
1. `resolveEditability` truth table: defaults (all true); `editable:false` → both false;
   `editable:false, eventStartEditable:true` → start true, duration false; `disableDragAndDrop:true` → both false;
   `disableDragAndDrop:true, editable:true` → both true; event `editable:false` under calendar true → both false;
   event `startEditable:true` under calendar `editable:false` → start true; event `editable:true,
   durationEditable:false` → start true, duration false.
2. A bar for an event with `startEditable:false` is not draggable (render the calendar through the existing test
   provider and assert the bar has no drag listeners/attributes, or that a simulated drag does not start —
   follow how existing drag unit tests check this).
3. `eventAllow` returning false makes the candidate placement `isDropAllowed: false` and the drop commit nothing;
   it receives the pre-drag event and the candidate's start, end, allDay and resourceId.

e2e (`apps/e2e/tests/drag.spec.ts` or `behaviour.spec.ts`, real pointer; add query params in
`apps/e2e/src/harness-config.ts`: `editable`, `eventStartEditable`, and `eventAllow=no-weekends`, a named
predicate that refuses any placement starting on Saturday or Sunday):
4. `&editable=false`: dragging an event moves nothing and publishes no change.
5. A scenario event with `editable: false` (add to an existing fixture in `apps/e2e/src/scenarios.ts` only if no
   query param can express it) stays put while its neighbour still drags.
6. `&eventAllow=no-weekends`: hovering a weekend cell shows the not-allowed cursor on `document.body`; releasing
   there leaves the event where it was and publishes nothing; dropping on a weekday moves it.
7. Upgrader: `&disableDragAndDrop=true` (add the param if absent) behaves exactly as before this change.
