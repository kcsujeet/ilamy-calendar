## Changes (follow-up to #256)

- **[calendar/droppable-cell]**: corrected the `getCellRange` doc comment and the `slotDurationMinutes` prop doc. Both said the cell range follows the *view* and implied resource grids honour `slotDuration`. What actually selects the branch is whether the caller passes `minute`, and `slotDuration` is only read by `VerticalEngineView` (`view-renderer.tsx`), so resource calendars, which default to the horizontal engine, report one-hour cells whatever `slotDuration` is set to.

## Notes

- The behavior #256 landed is the right one and matches the convention: a slot click reporting `start … start + slotDuration` is what FullCalendar's `slotDuration`/`dateClick` and Google Calendar both do. Citing it here because the standards rule asks for it and #256's own log did not.
- **#255 is only fixed for the vertical engine.** The horizontal engine never receives `slotDuration` and never passes `minute`, so its cells are whole hours (day-horizontal) or whole days (month/week-horizontal). Sub-hour horizontal cells would be a timeline view, which this library does not have. Deliberately left as-is and documented rather than "fixed": there is no failure to point at today. Revisit if a timeline view is ever added.
- Considered making `slotDurationMinutes` required on `GridCell` too, mirroring what #256 did for `DroppableCell`. Rejected: `GridCell`'s `= 60` default is only reached by horizontal callers, where the value is never read (no `minute` means `getCellRange` takes the hour branch), so requiring it would add a meaningless `60` to three call sites with no failure prevented.
- Fallow 3.0 release notes state no breaking changes: CLI flags, configuration and JSON output contracts are unchanged, and the major marks CSS analysis landing inside `fallow audit`. The new `css-token-drift` and `raw-style-value` findings are report-only until opted into via `rules`, so the gate behavior is unchanged. `@v2` -> `@v3` is required to keep receiving releases.
