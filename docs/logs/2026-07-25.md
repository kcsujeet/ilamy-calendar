# Development Log - 2026-07-25

## Changes

- **[release]**: Merged PR #239 (sub-hour business hours, closes #237) and PR #242 (date-picker `RangeError`, external contribution). Both on main, unreleased.

- **[utils/dayjs]**: Closed the class of bug #242 fixed one instance of. The configured dayjs forwards every constructor argument to `dayjs.tz()`, whose second parameter is a timezone, so `dayjs(input, 'YYYY-MM-DD')` threw `RangeError: invalid time zone` at runtime — while type-checking cleanly, because the module exported the wrapper `as typeof dayjs` and thereby advertised dayjs's `(date, format, strict)` overloads. The export is now typed as a one-argument constructor intersected with dayjs's statics (`DayjsStatics` mapped type drops the call signatures), so the mistake is a compile error instead of a runtime throw. Format parsing was never supported here anyway: it additionally requires the CustomParseFormat plugin, which this module deliberately does not extend. Verified non-breaking: monorepo type-check passes with zero errors across all packages.

- **[recurrence/date-picker]**: Locked the timezone contract that makes #242's fix correct, which no test covered. `onChange` reports start of day in the configured timezone, which east of UTC is the previous UTC day; correctness depends on the sole consumer (`recurrence-editor`'s `setUntil`) normalizing with `endOf('day')` in the same zone. Two tests pin this (Asia/Tokyo instant, plus the endOf-day round trip landing back on the picked day and containing a 23:00 occurrence), and the prop now documents the contract for the next consumer.

- **[utils infra]**: `@ilamy/utils` had no test runner. Added a `test` script so the root fan-out (`bun run --filter '*' --if-present test`) picks it up, plus `types: ["bun"]` in its tsconfig — unlike the other packages it does not resolve the root `@types/bun` automatically, so `bun:test` imports failed to type-check.

## Notes

The type test is the red/green mechanism for a types-only change: `tsc` reports `Unused '@ts-expect-error' directive` when the two-argument call stops being an error, so the guard fails loudly if the narrowing is ever reverted. Confirmed red before implementing (that exact error was the only one) and green after.

The timezone guard was verified load-bearing by swapping the parse to `dayjs.utc(raw)`, the most plausible "simplification": the Asia/Tokyo instant test fails. Worth knowing the round-trip test alone does not catch that, so keep both.
