# Development Log - 2026-08-13

## Changes

- **[calendar/event-form]**: Fixed #248 Part A — the form dropped nothing and kept everything, which is the wrong way round: it set hour and minute but left seconds and milliseconds untouched, so residue rode into stored events. Both builders now go through one `atMinute(date, time)` helper that ends with `.second(0).millisecond(0)`. The residue's source is the **+ New** path: `openEventForm()` with no arguments seeds `start` from `currentDate`, which originates in `dayjs()` and therefore carries the wall-clock seconds of page load, while an End Date picked from the calendar arrives clean at `00:00:00.000`. Mixing the two made a "12:00 AM to next-day 12:00 AM" event 23:59:27 long instead of 24h.

- **[calendar/interaction]**: `openEventForm` truncates its draft start to the minute for the same reason. This is not redundant with the builders: a consumer using `renderEventForm` receives `selectedEvent` directly and can save it without ever passing through them, and `openEventForm` is public API through the context. An explicitly passed `end` is left alone, since that is the caller's own value (a day cell deliberately passes `endOf('day')`).

- **[tests]**: Six new cases. Four pin that both builders clear seconds and milliseconds (timed and all-day paths), one pins the midnight-to-midnight duration at exactly 86,400s, one pins the seeded draft on a whole minute. The duration case is asserted as a **duration, not a column count**, deliberately: the column count is what #248 Part B changes, so pinning spans here would have to be rewritten by that work.

## Notes

**Why this looked like a prod-only ghost.** The symptom was that identical events spanned different numbers of days: May 11 to May 12 and May 19 to May 20 rendered as two-day bars while May 13 to May 14 rendered as one. `layoutHorizontal` classifies multi-day with `end.diff(start, 'day') > 0`, and dayjs truncates, so 23:59:27 becomes `0` and the event takes the single-column path. Whether an event was affected depended on **the second at which the page loaded** and on whether the user picked the start date from the calendar (clean) or accepted the seeded one (dirty). Reproducing it required driving the real form; hand-constructed events are always clean, which is why several rounds of probing missed it.

**Why the existing tests never caught it.** Every case in `event-form-utils.test.ts` passed `new Date('2025-01-15T00:00:00.000Z')`, already clean. The new `dirtyDate` fixture is the whole point.

**Scope check, done before editing.** A sweep for `\.hour(...)\.minute(` found four other call sites. `droppable-cell.tsx` and `dnd-utils.ts` both build from cell dates, and those are clean at the source (`getDayHours` already ends with `.second(0).millisecond(0)`, day cells derive from `startOf('week')`/`startOf('day')`), so they need nothing. The playground seed uses `dayjs().startOf('month')`, also clean. `date-utils.ts:94` was the existing precedent for the normalization pattern used here.

## Part B: exclusive `end` (#248)

- **[layout]**: `horizontal.ts` steps back a minute before resolving the end column at EVERY granularity, not only for hour grids. `end` is exclusive, so an event ending at midnight stops as that day begins and must not claim its column, exactly as one ending on the hour never claimed that hour's row. RFC 5545 §3.6.1 calls DTEND "the non-inclusive end of the event"; the Google Calendar API documents `end` as "The (exclusive) end time of the event".

- **[events/pipeline]**: `eventOverlapsRange` no longer matches an event whose `end` equals the range's first instant. Its `start` stays inclusive, so an event beginning at the range's last instant still matches. Without this, a `00:00`-to-`00:00` event appeared in the following day's list as well.

- **[event-form]**: An all-day `end` is stored as the midnight AFTER the last covered day. The form still shows that last day and converts on save, which is the split Google draws between its exclusive API and a UI that never asks for a midnight end. An all-day end that is not on a midnight boundary predates this convention and is displayed untouched, so existing data keeps reading correctly.

- **[droppable-cell]**: A day cell's range ends at the next midnight rather than `23:59`, matching the hour and 15-minute branches that already ended on the next slot boundary. This is a public contract change: it reaches `CellInfo.end` through `onCellClick` and the `data-end` attribute the drag-to-create plugin parses.

- **[docs]**: `types-and-interfaces.md` gained an "`end` is exclusive" section with the conversion rules; the website's `components/calendar.mdx` documents it for consumers and its all-day example no longer sets `end` equal to `start` (which under this convention covers no days at all); `help/migration-to-v2.mdx` gained three behavior-change entries and a checklist line.

## Notes (Part B)

**The span tests did not exist before this.** Flipping the layout line on its own left all 1140 tests passing, which is why `horizontal.test.ts` gained explicit column-count cases first: midnight-to-midnight covers one day, ending during the second day covers two, a conventional three-day all-day event covers three, and a zero-length event still covers one.

**Five existing tests pinned the old inclusive cell range** and were updated deliberately, not worked around: two in `droppable-cell.test.tsx` (`isCellDisabled` and `getCellClassName` receive `CellInfo`), one in `vertical-grid-col.test.tsx` (a daily cell now spans 24 hours, not 23), and the `onCellClick` month-view cases in both calendar test files.

**The export needed no code change.** It writes whatever `end` it is given, and its fixtures were already exclusive; the defect was that the form fed it `23:59`. The new case builds the event through the form's own helpers so the two modules stay honest about each other.

**Left alone deliberately**: the effect that forces `endTime` to `23:59` when All day is toggled on. `buildEndDateTime` ignores that value for all-day events now, so it changes nothing, and removing it would alter what the time picker shows after toggling all-day off. That is a separate cleanup.

**Known UX consequence**: clicking a month day cell now prefills the form's End Date as the following day at 12:00 AM rather than the same day at 11:59 PM. Both describe the same span under the convention, but the prefill reads oddly. Worth a follow-up in the form if it bothers users.
