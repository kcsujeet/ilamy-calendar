## Changes (demo business hours)

- **[demo]**: The playground (demo app and the website's demo page) defaults `enableBusinessHours` to `false`. In 3.x business hours refuse clicks, moves and resizes on closed cells, so on a weekend or after hours the seed events a visitor grabbed first would not budge, with only a not-allowed cursor, and it was reported as "resize is broken". Off matches FullCalendar's `businessHours` default. Switching it on still shades and restricts as before (checked on the dev demo and on an `astro build` + `astro preview` of the website).
- **[e2e]**: A second Playwright project, `demo`, drives the real `apps/demo` at its default settings and seed events (`apps/e2e/demo-tests/demo-defaults.spec.ts`), the clock pinned to Sunday 2026-10-25 10:00 UTC: a week-view resize by one slot, a month-view resize by one day and a week-view move by one slot, each with a real pointer. All three failed with business hours on (each bar stayed where it was) and pass with the new default. `bun run e2e` runs both projects, so the existing CI job covers it; the demo server's port comes from `E2E_DEMO_PORT` (default 4210).
- **[docs]**: `docs/migration-v4.md` records the planned 4.0 change: business hours (and month padding days) only shade, and restricting becomes opt-in through `eventConstraint: 'businessHours'` and `selectConstraint: 'businessHours'`, with FullCalendar doc URLs and v7.1.1 source citations (`dateClick` fires outside business hours; padding days take drops, clicks and selection while `showNonCurrentDates` is true). `docs/roadmap.md` moves the `'businessHours'` constraints into 4.0.5 so no release drops the restriction without its replacement; 4.1.2 keeps the other constraint values, overlap, `groupId` and `validRange`. The website's Business Hours and resource pages and the plugin guide's `data-disabled` row mark what changes in 4.0.

## Changes (build resolution)

- **[build]**: Resolves the publish-check follow-up above. The published build resolves `@ilamy/utils` to source as one module. `packages/ui/tsconfig.json` had no `paths`, and Bun resolves each import through the tsconfig nearest the importing file, so `@ilamy/ui`'s `current-time-indicator.tsx` reached `@ilamy/utils/dayjs` through the package exports (`packages/utils/dist`). From a fresh clone `bun run build:lib` (and so `release`/`release:dry`) failed with "Could not resolve: @ilamy/utils/dayjs"; in an older checkout it bundled whatever stale `dist` was there, so the 3.3.0 tarball has two copies of the dayjs configuration, the ui one built before #378.
- **[build]**: ui now maps `@ilamy/utils/dayjs` and `/helpers` to source like the calendar and plugins. Its own build (`bunup`, `dts.inferTypes`) uses a new `tsconfig.build.json` that drops the mapping: with it, the declaration bundler tried to inline `../utils/src` and failed. ui's own `dist` is byte-identical to before.
- **[docs]**: `docs/timezones.md` (the double-load paragraph), `docs/monorepo-architecture.md` (the base tsconfig has no `paths`; each package maps its own) and `AGENTS.md` updated.

Tests that load a plugin still load two copies: plugin source imports `@ilamy/calendar`, which resolves to the built `dist`. That is by design (plugins consume the public API), and it is why calendar unit tests need a build first.
