# Development Log - 2026-10-02

## Changes

- **[vertical grid navigation]** (#300): Moving a week in a vertical time grid no longer remounts every cell, which made a 15-minute resource week take seconds to navigate.
  - Cause, from a CPU profile of three week navigations: about half the time was `DroppableContainersMap` in `@dnd-kit/core`. Every `RegisterDroppable` and `UnregisterDroppable` copies the whole container map (`core.esm.js:2628`, `:2673`, v6.3.1), so N droppables cost O(N²) to register.
  - Navigation paid it twice. The column keys and the cell keys inside a column both carried the column id, which carries the date, so React remounted all cells. The droppable id carried the date too, and `useDroppable` re-registers when its id changes (`useEffect(..., [id])`), so even a kept cell re-registered.
  - Fix: column and cell keys are positional, and `DroppableCell` takes its droppable id from `useId()`. The drop still reads the date from `data`, which `useDroppable` keeps in a ref refreshed every render (`useLatestValue`).
- **[keys]**: Removed `keys.droppable.dayCell` and the `id` prop of `DroppableCell`; nothing reads a droppable id other than dnd-kit itself.

- **[published types]** (#302): the shipped declarations referenced `dayjs.Dayjs3`, `dayjs.ManipulateType3` and `React.ReactNode3`, none of which exist, so a consumer type-checking with `skipLibCheck: false` failed.
  - Cause: bunup's declaration bundler (`@bunup/dts` 0.14.53, latest; `bunup` 0.16.32, latest) renames a local type on a name clash, and also renamed the matching member of a qualified name. `export type Dayjs = dayjs.Dayjs` became `type Dayjs3 = dayjs.Dayjs3`. Which qualified names get hit depends on clashes anywhere in the bundle, so it is not one line.
  - Fix: exported types use named type imports instead of qualified names: the dayjs aliases and `ConfiguredDayjs` (`utils/src/dayjs.ts`), and `ReactNode`/`Context`/`FC` in the calendar props, context and provider. The bundler now emits `type Dayjs3 = DayjsInstance` from `import { Dayjs as DayjsInstance } from "dayjs"`, which is valid.
  - The reporter also asked for a check against the generated types: `check:dist-types` runs a strict `tsc` (`packages/calendar/tsconfig.dist.json`, standalone, no `paths`) over `dist/**/*.d.ts`. Added to CI after the build, to the root `ci` script, and to `release`/`release:dry` before publishing.
  - Red first: the check failed with 7 errors on `c636da8`, the six the reporter listed plus one they missed (`React3.ReactNode3` in `dist/testing/index.d.ts`). Green after the fix.
- Fallow warns about duplicated prop interfaces across `types/index.ts`, `provider.tsx` and `context.ts`. Pre-existing; not touched here.

- **[drag hover tint]** (#299): the cell under a dragged event no longer takes the `hover:bg-accent` tint, which painted a second colour (the consumer's accent) beside the drop tint. Hovering without a drag still tints, which the reporter wants for creating events. The drop tint stays: it shows where the event will land.
  - `CalendarDndContext` wraps its children in a `display: contents` div carrying `data-dragging="true"` while `dragPreview` is set, i.e. while a drag is over the calendar. `contents` keeps it out of the layout; `children` is the same element, so React does not re-render the grid for it.
  - Day/month cells (`grid-cell.tsx`) and time slots (`vertical-grid-col.tsx`) use `not-in-data-dragging:hover:bg-accent`. Tailwind 4.3.3 generates `.x:not(:where([data-dragging]) *):hover`. `not-*` and `in-*` are both v4.0 variants (https://tailwindcss.com/blog/tailwindcss-v4), inside the `^4.2.2` peer range; the stacked form is verified on 4.3.3 only.
  - Headers, pickers and year cells keep their hover: they are not drop targets.
  - Red first: the two "under a drag" e2e specs got the accent `oklch(0.97 0 0)` instead of the resting `oklch(1 0 0)`. The two "nothing is dragged" specs pin that hover still tints.
  - No unit test: happy-dom has no layout, so dnd-kit never reports a drop target and `dragPreview` cannot be set without a real pointer. The behaviour is pinned in e2e only.

- **[header at every width]** (#298): the header now looks right from a phone to a desktop.
  - The report: on a phone, the navigation cluster (previous/next, Today, the date picker) could not wrap or shrink, so the day view's label ("Wed, Mar 12, 2025") pushed it past both edges of the header and the outer buttons were cut off. Fix: that cluster wraps, centered, when it cannot fit (the reporter's `flex-wrap` + `justify-center`).
  - That alone exposed the wrong breakpoints. A sweep from 280 to 1300 px, day/week/month/year, English and German, found the row turning on before it fit: the navigation wrapped beside a one-line action cluster at 512-552 px (day) and 768-776 px (day, when the segmented switcher appears), and German week at 512-516 px. On `main` the same widths did not wrap; the navigation's content spilled under the actions instead.
  - Measured row needs, day view (the longest title): compact row 340 + 214 + 8 = ~562 px; with Export/New labels ~651 px; with the segmented switcher 340 + 422 + 8 = ~770 px. Breakpoints moved to where each fits: row `@lg` (512) -> `@xl` (576); segmented switcher `@3xl` (768) -> `@4xl` (896). Labels stay at `@2xl` (672). Container sizes from https://tailwindcss.com/docs/responsive-design.
  - After: no clipping, overlap, or mixed layout at any width in the sweep. The only wrap left is the intended one in the stacked phone layout, below ~345 px.
  - Not taken: dropping the year from the day label. It only helps English-length labels; wrapping covers longer locales.
  - Revert-proofed: removing the whole change fails at 300 px (clipping); reverting only the breakpoints fails at 512 px (row); reverting only the switcher breakpoint fails at 768 px.
