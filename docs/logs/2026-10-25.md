## Changes

- **[build]**: The published build resolves `@ilamy/utils` to source as one module. `packages/ui/tsconfig.json` had no `paths`, and Bun resolves each import through the tsconfig nearest the importing file, so `@ilamy/ui`'s `current-time-indicator.tsx` reached `@ilamy/utils/dayjs` through the package exports (`packages/utils/dist`). From a fresh clone `bun run build:lib` (and so `release`/`release:dry`) failed with "Could not resolve: @ilamy/utils/dayjs"; in an older checkout it bundled whatever stale `dist` was there, so the 3.3.0 tarball has two copies of the dayjs configuration, the ui one built before #378.
- **[build]**: ui now maps `@ilamy/utils/dayjs` and `/helpers` to source like the calendar and plugins. Its own build (`bunup`, `dts.inferTypes`) uses a new `tsconfig.build.json` that drops the mapping: with it, the declaration bundler tried to inline `../utils/src` and failed. ui's own `dist` is byte-identical to before.
- **[docs]**: `docs/timezones.md` (the double-load paragraph), `docs/monorepo-architecture.md` (the base tsconfig has no `paths`; each package maps its own) and `AGENTS.md` updated.

## Notes

Alternative considered: make `build:lib` build `@ilamy/utils` first. That fixes the fresh clone and staleness but still ships two copies (utils `dist` + source), so it was rejected.

Verified from a fresh `git worktree add` + `bun install` (no `dist` anywhere): `bun run release:dry` succeeds, and the built `dist` has one import of each `dayjs/plugin/*.js` (the 3.3.0 tarball has two). `bun run ci` and `bun run e2e` (1,292) pass.

The `month.test.tsx` "across a DST transition" case passes under `TZ=Pacific/Auckland` before and after this change, and also with a utils `dist` built from before #378 and before #328, so the failure recorded on 2026-10-12 no longer reproduces and its cause is unverified (written so in `docs/timezones.md`). The whole calendar suite under `TZ=Pacific/Auckland` fails the same 101 tests at HEAD and with this change: those are the expected UTC-shaped expectations `docs/timezones.md` describes.

Tests that load a plugin still load two copies: plugin source imports `@ilamy/calendar`, which resolves to the built `dist`. That is by design (plugins consume the public API), and it is why calendar unit tests need a build first.
