# 3.3.9 Ref API Implementation Plan

> TDD (superpowers:test-driven-development). Part of `docs/roadmap.md`, release 3.3 (formerly 3.4.3).

**Goal:** Consumers can drive the calendar from outside it (their own toolbar, a sidebar, a "jump to" button) through a
`ref`, with the same API they already get from `useIlamyCalendarContext()` inside it.

## The standard
- React 19: `ref` is a regular prop on function components; `forwardRef` is no longer needed
  (https://react.dev/reference/react/forwardRef). Expose a handle with `useImperativeHandle(ref, createHandle, deps)`
  (https://react.dev/reference/react/useImperativeHandle). The package's React peer is `^19.2.0`
  (`packages/calendar/package.json`), so no `forwardRef`.
- The convention exposes an imperative calendar API through a ref (`getApi()` on `@fullcalendar/react`'s ref,
  `Calendar.tsx:22-54` at v7.1.1) with navigation (`gotoDate`, `next`, `prev`, `today`, `changeView`), events
  (`getEvents`, `getEventById`, `addEvent`, `refetchEvents`) and `scrollToTime` (`api/CalendarApi.ts:35-83`).

## Decisions (record)
- `IlamyCalendar` accepts `ref?: React.Ref<IlamyCalendarApi>`. `ref.current` is exactly the object
  `useIlamyCalendarContext()` returns (one API, one set of names — roadmap D6 keeps ilamy's names; the migration
  guide maps them: `setCurrentDate`↔`gotoDate`, `nextPeriod`↔`next`, etc.). Not a second handle type.
- Add `scrollToTime(time: string)` (`'HH:mm'` or `'HH:mm:ss'`) to `IlamyCalendarApi`: scrolls hour grids to that
  time with the same proportional logic as the `scrollTime` prop (3.3.7a's use-scroll-to-time; reuse it, do not
  write a second scroller); no-op in views without an hour axis.
- `ref.current` must always read the latest state: either refresh the handle each render (deps = the API object) or
  make it a stable object whose methods read the latest API — choose the simplest that guarantees
  `ref.current.currentDate` is current after navigation and that method identities do not churn consumers' effects;
  record the choice.
- `IlamyResourceCalendar` (deprecated alias) gets the same `ref`.
- Out of scope (record): `select`/`unselect` (with selection, 4.1.3); a separate `useCalendarController` hook (the ref
  plus `headerComponent` cover custom toolbars).

## Where (verify): `components/ilamy-calendar.tsx`, `components/ilamy-resource-calendar.tsx`,
`hooks/use-smart-calendar-context.ts` / the public `useIlamyCalendarContext` and `IlamyCalendarApi` type,
`hooks/use-scroll-to-time.ts`, `packages/calendar/src/index.ts` (export nothing new beyond what is needed).
Harness: buttons outside the calendar in `apps/e2e/src/app.tsx` behind a `&externalToolbar=1` param that call
`ref.current` methods (next, prev, today, changeView, gotoDate to a fixed ISO date, scrollToTime '13:30',
refetchEvents with the async scenario) and print `ref.current.currentDate` / view.

## Tests first
Unit (render IlamyCalendar with a ref): ref.current exists after mount and is the same shape as the hook's API;
next/prev/today/changeView/setCurrentDate through the ref update the rendered view and `ref.current.currentDate`;
add/update/delete through the ref fire the usual callbacks; scrollToTime('13:30') sets the scroll container's
scrollTop to the 13:30 position (and is a no-op in month); refetchEvents through the ref refetches with a fetcher;
the deprecated alias forwards the ref; method identities are stable across a navigation (if that is the chosen rule).
e2e: external toolbar buttons drive navigation, view changes and scrollToTime in the real UI; the printed current
date updates.

## Global constraints
No breaking change; no `forwardRef`; configured dayjs only; no `!`, no `any`, `.at()`, named exports, name every
condition; unit AND e2e first; revert proof; machine-zone-independent new tests; docs (`docs/hooks-and-context.md`,
`docs/types-and-interfaces.md`, website `use-ilamy-calendar-context.mdx` + props page "Controlling the calendar from
outside", `docs/api-parity-checklist.md`, roadmap row 3.3.9). Public text never frames this as parity; cite behaviour
with URL/file:line. No dev log, no CHANGELOG.
