# v4.0 Plan — Step 1: Temporal Date Core (`@ilamy/utils/temporal`)

**Target release:** `v4.0.0` (one major release; items 1–9 in `docs/roadmap.md` land together on `v4.0.0`, built in reviewable chunks).
**Branch:** `roadmap/4.0-temporal-core` (additive foundation — breaks zero existing 3.x code).
**Placement:** `@ilamy/utils` (`packages/utils/src/temporal.ts`, exported as `@ilamy/utils/temporal`).

## Goal

Replace the `dayjs` date engine with a pure, stateless, tree-shakeable Temporal date core built on `temporal-polyfill/fns/*` and `Intl.DateTimeFormat`. Eliminate the module-global timezone (`dayjs.tz.setDefault`) and every machine-zone DST leak recorded in `docs/timezones.md`.

## Standards & Citations

- **RFC 5545 §3.3.5** (Date-Time): floating/wall-clock times falling in a spring-forward gap shift forward by the gap; repeated autumn times take their first occurrence. Temporal's `disambiguation: 'compatible'` implements this exact rule.
- **RFC 5545 §3.6.1** (DTEND): event `start` is inclusive and `end` is exclusive (`overlapsRange`).
- **FullCalendar v7** (`packages/headless-calendar/src/marker.ts`, `env.ts`, v7.1.1; https://fullcalendar.io/docs/timeZone):
  - Uses `temporal-polyfill` internally (tree-shakeable, side-effect free, no global `Temporal` mutation).
  - Public API exposes native `Date` and ISO 8601 strings — never `Temporal` objects.
  - Offset-less strings are parsed in the calendar's configured zone; offset-carrying strings keep their instant and render in the configured zone.
- **Bundle measurement** (`bun build --minify` + gzip, measured 2026-11-18):
  - Current `dayjs@1.11.23` + 8 plugins: 16.1 KB raw / 5.9 KB gzip.
  - `temporal-polyfill@1.0.8` `fns/*` (named imports, calendar subset): 36.5 KB raw / 13.8 KB gzip (+7.9 KB gzip; external dependency).
  - Wildcard `import *`: 87.4 KB raw / 26.9 KB gzip → **named imports only**.

## Public Surface (`@ilamy/utils/temporal`)

All functions are pure and take an explicit `ZonedDate` (`ZonedDateTimeRecord` from `temporal-polyfill/fns/ZonedDateTime`) or explicit `timezone?: string` — zero module-global timezone state.

### Types
- `ZonedDate` (`ZonedDateTimeRecord`)
- `DateInput = ZonedDate | Date | string | number`
- `DateUnit = 'year' | 'month' | 'week' | 'day' | 'hour' | 'minute' | 'second' | 'millisecond'`
- `BoundaryUnit = 'year' | 'month' | 'week' | 'day' | 'hour' | 'minute'`

### Functions
1. **Zone & creation**
   - `resolveZone(timezone?: string): string` — returns `timezone` or `Now.timeZoneId()`.
   - `now(timezone?: string): ZonedDate`
   - `parseDate(input: DateInput | undefined, timezone?: string): ZonedDate | undefined` — returns `undefined` on missing/invalid input (never throws). Offset-carrying strings / `Date` / `number` / `ZonedDate` keep their instant in `zone`; offset-less strings anchor in `zone` with `disambiguation: 'compatible'`.
   - `fromFields(fields: { year: number; month: number; day: number; hour?: number; minute?: number; second?: number; millisecond?: number }, timezone?: string): ZonedDate`
   - `withZone(date: ZonedDate, timezone: string): ZonedDate`
2. **Boundaries**
   - `startOf(date: ZonedDate, unit: BoundaryUnit, weekStart?: number): ZonedDate` (`day` uses `ZonedDateTime.startOfDay()`; `hour`/`minute` use `round({ roundingMode: 'floor' })`; `week` respects `weekStart`, 0 = Sunday .. 6 = Saturday).
   - `endOf(date: ZonedDate, unit: BoundaryUnit, weekStart?: number): ZonedDate` (1 millisecond before the next unit's `startOf`).
3. **Arithmetic**
   - `add(date: ZonedDate, amount: number, unit: DateUnit): ZonedDate`
   - `subtract(date: ZonedDate, amount: number, unit: DateUnit): ZonedDate`
   - `withTime(date: ZonedDate, time: { hour?: number; minute?: number; second?: number; millisecond?: number }): ZonedDate`
4. **Readers & serialization**
   - `getFields(date: ZonedDate)` → `{ year, month, day, hour, minute, second, millisecond, dayOfWeek, daysInMonth }` (note: `dayOfWeek` normalized to 0 = Sunday .. 6 = Saturday to match JS `Date.getDay()` and `firstDayOfWeek`).
   - `toEpochMs(date: ZonedDate): number`
   - `toDate(date: ZonedDate): Date`
   - `toUtcIso(date: ZonedDate): string`
   - `toOffsetIso(date: ZonedDate): string`
   - `dayKey(date: ZonedDate): string` (`YYYY-MM-DD` in `date`'s zone)
   - `offsetMinutes(date: ZonedDate): number`
5. **Comparison & diffs**
   - `isBefore`, `isAfter`, `isSameInstant`, `isSameOrBefore`, `isSameOrAfter` (exact `epochNanoseconds` comparisons).
   - `isSameDay(a: ZonedDate, b: ZonedDate): boolean`
   - `overlapsRange(interval: { start: ZonedDate; end: ZonedDate }, start: ZonedDate, end: ZonedDate): boolean` (exclusive `end`).
   - `wallClockDiff(end: ZonedDate, start: ZonedDate, unit: 'day' | 'hour' | 'minute'): number`
   - `elapsedDiff(end: ZonedDate, start: ZonedDate, unit: 'day' | 'hour' | 'minute' | 'millisecond'): number`
   - `minDate(a: ZonedDate, b: ZonedDate): ZonedDate` / `maxDate(a: ZonedDate, b: ZonedDate): ZonedDate`
6. **Formatting (`Intl`)**
   - `formatDate(date: ZonedDate, options: Intl.DateTimeFormatOptions, locale?: string): string` — always passes `timeZone: date.timeZone`, caches `Intl.DateTimeFormat` by key.

## Acceptance Criteria & TDD Plan

1. **Unit tests first** (`packages/utils/src/temporal.test.ts`):
   - Parsing: `Z`, `±HH:MM`, `±HHMM`, offset-less date/datetime, `Date`, epoch ms, `ZonedDate`, invalid inputs → `undefined`.
   - DST transitions: spring-forward gap (shifts forward), repeated autumn hour (first occurrence), repeated midnight (e.g. `America/Havana`, `America/Sao_Paulo`, `Asia/Beirut`).
   - Boundaries (`startOf`/`endOf`) for every unit including `week` with `weekStart` 0..6.
   - Multiple zones simultaneously in the same process with zero interference.
   - `overlapsRange` exclusive-end edge cases (including zero-duration and inverted intervals).
   - `wallClockDiff` vs `elapsedDiff` across spring-forward and fall-back days.
   - `formatDate` always honors `date.timeZone`, never the machine's zone.
2. **Multi-machine-zone `Intl`-reference acceptance suite** (`docs/timezones.md:361-373`):
   - Run in child processes with `TZ` set to `UTC`, `America/Vancouver`, `Europe/London`, `America/Havana`, `Pacific/Auckland`.
   - Test 14 awkward zones (midnight DST changes, half-hour offsets, southern hemisphere, Chatham/Lord Howe, etc.) across every clock change of 2025/2026 against an `Intl.DateTimeFormat`-only reference.
   - **0 mismatches** across all zones and all machine `TZ`s.
3. **Gates**: `bun run ci` passes cleanly; `temporal-polyfill` is externalized in `packages/utils/bunup.config.ts` and `packages/calendar` continues to build and pass all tests untouched.
