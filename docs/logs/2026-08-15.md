# Development Log - 2026-08-15

## Changes

Three review findings on PR #250, each verified by measurement before being fixed.

- **[layout]**: `partitionAndSortEvents` asked a DURATION question (`end.diff(start, gridType) > 0`) where the answer needed a BOUNDARY question. dayjs truncates, so anything shorter than a whole unit was classified single-unit and placed with `endCol: col`, throwing away the correct span `computeColumnSpan` had already worked out. An 18:00-to-06:00 event vanished from its second day in month view, and a 09:30-to-10:15 one from its second hour in the horizontal hour grid. Classification now compares the start's unit with the last unit the event OCCUPIES, the same notion the span math uses.

- **[event-form]**: Clicking a month cell and ticking "All day" saved a two-day event for a single day. A day cell's range ends at the next midnight, so the End Date prefills as the following day. That date means a boundary while the event is timed but the last day COVERED once it is all-day, and `buildEndDateTime` added a day on top. The toggle now steps the date back when the end sits on midnight. Turning "All day" off is unchanged and still produces a same-day timed event.

- **[agenda]**: `appearsOnDay` tested only the end, which dropped a zero-duration all-day event: its START is what places it. It now uses the same three cases as the core's `eventOverlapsRange` (starts in the day, ends in the day, spans it), so the agenda and the grid cannot disagree. The one-day and multi-day cases from yesterday still hold.

## Notes

**Measured before fixing, in every case.** The layout claim was checked by placing the events and reading the emitted columns (`18:00 -> 06:00 : startsAt=1 units=1`); the form claim by driving the real cell-click-then-toggle flow and reading what `onEventAdd` received (`2026-05-13 -> 2026-05-15`, two days covered); the agenda claim by comparing `eventOverlapsRange` (true) against the plugin's predicate (false) for the same event. A review comment is a hypothesis like any other.

**Behavior change worth knowing**: events whose `end` precedes their `start` used to match neither filter in `partitionAndSortEvents` and disappeared entirely. The partition is now total, so they render as a single chip at their start. Predictable beats invisible, but it is a change, not a fix anyone asked for.

**The agenda keeps its own predicate** rather than importing the core's. Its rule is genuinely different (all-day repeats under each covered day, timed appears once under its start day); only the overlap half needed to match. Sharing it would mean relocating `eventOverlapsRange` to `@ilamy/utils`, which is the right move if a third caller ever appears.

## Second review round

Two more findings, both verified by measurement first.

- **[event-form]**: The all-day step back applied unconditionally whenever the end time was midnight, so an event whose end sits on the SAME day as its start (a zero-length one) had its End Date moved to the day BEFORE the start, visibly, and `buildEndDateTime` adding a day back then saved another zero-length event instead of the one-day event the user asked for. The step now applies only when the end sits on a later day.

- **[recurrence]**: Yesterday's strict end test dropped a zero-duration occurrence landing exactly on the range start: its START is what places it, not its end. The filter now uses the same three cases as the core's `eventOverlapsRange`, so an occurrence is kept here exactly when the host would keep it. The boundary case from yesterday (an occurrence ENDING at the range start is excluded) still holds.

- **[events/pipeline]**: Added the zero-duration case to `eventOverlapsRange`'s own tests. Both plugins now mirror that predicate, and the invariant they mirror was itself unpinned.

After fixing them, the sweep for that shape came back clean: `pipeline` already keeps such an event through `startsInRange`, `horizontal` classifies it single-unit and paints it, `dnd-utils` makes no comparison.

**The three-case overlap predicate now exists in three places** (`lib/events/pipeline.ts`, the agenda's `appearsOnDay`, the recurrence range filter). That is precisely the duplication `.agents/rules/change-impact.md` names as the cause of this whole class of bug, and `.agents/rules/architecture.md` says shared logic belongs in `@ilamy/utils`. Relocating `eventOverlapsRange` there, with both plugins importing it, is the follow-up that would stop these three drifting apart again. Not done here: it touches three packages and is a refactor rather than a review fix.

## Follow-up: one home for the overlap predicate

- **[utils]**: `overlapsRange` now lives in `@ilamy/utils/helpers`, and the core, the agenda plugin and the recurrence plugin all call it. It had grown three private copies, which is what `.agents/rules/architecture.md` forbids and what `.agents/rules/change-impact.md` names as the cause of this whole bug class: the grid said a one-day event, the agenda said two.

- **[utils]**: Typed over `{ start: Dayjs; end: Dayjs }` rather than `CalendarEvent`, so `@ilamy/utils` needs no dependency on `@ilamy/types`. `CalendarEvent` satisfies it structurally, so no call site changed shape. The name lost its `event` prefix because the helper knows nothing about events: cells, selections and view ranges are the same shape.

- **[agenda]**: `appearsOnDay` keeps its own rule (all-day repeats under each covered day, timed appears once under its start day) and delegates only the overlap half.
