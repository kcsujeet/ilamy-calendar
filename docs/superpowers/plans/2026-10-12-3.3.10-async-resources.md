# 3.3.10 Async resources Implementation Plan

> TDD (superpowers:test-driven-development). Part of `docs/roadmap.md`, release 3.3 (formerly 3.4.2).

**Goal:** `resources` can be an async function, like `events` (3.3.8), and consumers hear when the resource list is
set or changes.

## The standard (FullCalendar docs; the resource plugin is premium, so docs only)
- `resources` as a function `(fetchInfo, success, failure)` or returning a Promise; `fetchInfo` has start, end
  (exclusive), startStr, endStr, timeZone, populated only when `refetchResourcesOnNavigate` is true
  (https://fullcalendar.io/docs/resources-function).
- `refetchResources()` re-calls it (https://fullcalendar.io/docs/Calendar-refetchResources).
- `resourcesSet(resources)` is "Called after resource data is initialized OR changed in any way"
  (https://fullcalendar.io/docs/resourcesSet).
- `loading` also covers resource fetches when resources load (https://fullcalendar.io/docs/loading).

## Decisions (record)
```ts
export type ResourcesFetcher = (info: EventsFetchInfo, options: { signal: AbortSignal }) => Promise<Resource[]>
resources?: Resource[] | ResourcesFetcher
refetchResourcesOnNavigate?: boolean   // default false: fetch once on mount (and on refetchResources())
resourcesSet?: (resources: Resource[]) => void
```
- Reuse the 3.3.8 fetcher's machinery (abort superseded, ignore late results, failure keeps shown resources +
  `onEventsError`? — no: add `onResourcesError?` only if it falls out naturally; otherwise route resource failures to
  `onEventsError`… decide the simplest correct option and record it). Do NOT write a second copy of the abort/latest/
  loading logic: generalise `use-events-fetcher.ts` into one small fetcher hook used for both, if that keeps it simple;
  otherwise explain why not.
- `loading` is true while either events or resources are being fetched (one aggregate, as the convention).
- With `refetchResourcesOnNavigate={false}` (default) the info range is the range at mount; with true, every range
  change refetches (lazy rules as for events).
- `refetchResources()` on the context API (and therefore the ref from 3.3.9 if it lands first; otherwise the context).
- `resourcesSet` fires after the first resolved list and after every change (array prop change, fetch result), not on
  every render. For an array prop it fires once on mount and when the array identity changes.
- Events whose `resourceId` is not in the list behave exactly as today.

## Where (verify): `features/calendar/hooks/calendar-data/use-resource-lookups.ts`, `use-calendar-data.ts`,
`use-events-fetcher.ts` (3.3.8), provider/context/types, `components/ilamy-calendar.tsx`. Harness: an async
resources mode (`&resourcesFetch=delayed|failing`) publishing fetch logs and `resourcesSet` calls.

## Tests first
Unit: array resources unchanged; fetcher called once on mount with the visible range; refetchResourcesOnNavigate
refetches on navigation, default does not; superseded fetch aborted; failure keeps resources and reports; resourcesSet
fires once per change (not per render); aggregate loading with both fetchers; refetchResources.
e2e: delayed resource fetcher renders lanes after the delay in vertical and horizontal views; failing fetcher keeps
lanes; refetchResources; existing resource scenarios unchanged.

## Global constraints
No breaking change; configured dayjs only; no `!`, no `any`, `.at()`, named exports, name every condition; unit AND
e2e first; revert proof; machine-zone-independent new tests; docs (`docs/resource-calendar.md`, `docs/hooks-and-context.md`,
`docs/types-and-interfaces.md`, website resource page, `docs/api-parity-checklist.md` tick resourcesSet/resources as
function, roadmap row 3.3.10). Public text never frames this as parity; cite behaviour with URL/file:line. No dev log,
no CHANGELOG.
