# Development Log - 2026-07-27

## Changes

- **[release]**: Cut v2.0.3 — the header animation rework (#244) plus the month header vertical centering fix. Patch bump: no API change, visual only.

- **[views/headers]**: View headers now animate only their label, not the whole cell. Previously `AnimatedSection` **was** the header cell, so it carried `bg-background`, `flex-1`, padding and hover styles, and the entire cell slid and faded in on every navigation. The year view read better because its `AnimatedSection` sits inside the month card wrapping only the title row, leaving the card's border, background and padding static. Every header now follows that shape: a plain cell element holding layout, background, `data-testid` and click handler, with `AnimatedSection` inside wrapping just the `DayLabel` / `HourLabel` / weekday span.

- **[animations]**: Removed staggering everywhere, including the year grid, so all animated elements enter together. `TimeHeaderRow` lost its `delayStep` prop, and both `HEADER_STAGGER_DELAY` and `HOUR_STAGGER_DELAY` are deleted (the latter existed only so a 168-cell hour row would not cascade for ~8s). Enter duration raised from 200ms to 500ms in `AnimatedSection`.

- **[views/headers]**: Vertically centered the month view weekday labels. `month-header.tsx` was the only one of the seven header cells with no flex centering (`py-2 text-center font-medium bg-background flex-1 min-w-0`), so once the animation moved inside, the `inline-block` wrapper sat on the text baseline and the label rode high in the row. Added `flex items-center justify-center` to the cell. Same root cause as the hour-label regression below: an `inline-block w-full` wrapper between cell and text changes how the text is positioned, and only cells that already centered via flex were immune.

## Notes

Regression caught during review and worth remembering: `HourLabel` renders a bare text node with no element of its own, so it inherits alignment from whatever box wraps it. Moving `AnimatedSection` inside the hour cell put a `w-full` wrapper between cell and text, which made the cell's `justify-center` a no-op and left the hour labels pinned to the left edge of every column in the resource horizontal views. Fixed by putting `text-center` on the animated wrapper. `DayLabel` is immune because it centers its own content (`flex flex-col items-center` plus `text-center` on the weekday), which is why only the hour row broke.

`AnimatedSection` itself is otherwise untouched. Its `delay` prop is now unused but kept, since the component is shared by the view container, the year cards and event mounts, and reworking a shared component during a visual fix invites exactly the kind of regression above.

The 500ms duration lives in `AnimatedSection`, so it applies to all four consumers: header labels, the view-switch fade, year cards, and every event mount. If event mounts feel slow, the narrower fix is to keep the component at 200ms and pass `duration-500` per call site, which works because `cn` uses `twMerge` and a passed duration overrides the default.

`duration-500` was verified to actually generate rather than silently falling back to the plugin's 150ms default: the built demo CSS contains `animation-duration:.5s`. The `tailwindcss-animate` plugin maps `duration-*` to `animationDuration` from `{0, ...theme('transitionDuration')}`.

The week day header keeps its click-to-create behavior as a `div` with two `biome-ignore` lines rather than becoming a `button`, since that would change default styling and focus semantics.

## Changes (PR #241 review response, external contribution)

- **[utils/events]**: Fixed a real bug in the day-bucketing helper introduced by this branch: it treated "nearest preceding day start" as "the day containing this timestamp", which only holds for consecutive days. `useProcessedWeekEvents` receives the `hiddenDays`-filtered column list from `week.tsx`, so with Wednesday hidden a Wednesday event landed in Tuesday's bucket — where the per-day predicate it replaced had placed it nowhere — inflating `hiddenEventsCount` and the "all events" dialog. `DayIndex` now carries `dayEnds` alongside `dayStarts`, and membership comes from `daySpanOf`, which binary-searches both arrays. No per-day re-verification is needed: every index at or after `low` has `dayEnds[i] >= startMs` and every index at or before `high` has `dayStarts[i] <= endMs`, so each index between satisfies the inclusive overlap test, and an interval inside a gap yields `low > high`. Still O(n log d).
- **[utils/events]**: `dayIndexOf` now returns the day *containing* a timestamp, or -1 — including timestamps inside a gap or past the grid. It previously returned the nearest preceding index, which is why callers clamped. Those clamps were dead anyway (it could never exceed the last index), so they are gone along with the docstring that instructed callers to add them. `gridEnd` removed, superseded by `dayEnds`. Malformed-event handling extracted into `malformedEventDays`.
- **[utils/events]**: Added `countEventsByDay`, which produces the same per-day numbers without materialising the buckets. The year view renders only counts, so building 504 arrays to read their lengths allocated for nothing.

## Changes (PR #241 core mechanisms, recorded retrospectively)

The earlier section covered only the review response, so the three mechanisms the
PR is actually built on went unrecorded. They are the parts a future reader needs.

- **[utils/events]**: New `@ilamy/utils/events` module. `eventOverlapsRange` used to compare `Dayjs` instances (~1 222 ns per comparison); it now compares epoch millis (~4 ns). Event bounds are cached in a **`WeakMap` keyed on the event object**, not on a field of it and not on `event.id`. That choice is load-bearing: around 15 sites in this repo spread an event while replacing its dates — `{ ...event, start: occurrenceDate, end: newEndTime }` in `generateRecurringEvents` is the important one — so a cached field would travel with the spread and report the parent's instant for the child's dates. Wrong-day rendering, silently, with no error. Object identity makes every spread a cache miss, so the staleness bug is structurally impossible rather than merely avoided. `event.id` fails the same way and worse, since recurrence instance ids are derived per expansion. Measured 6 240 → 37 ns/event (168x), and the timezone penalty on this predicate disappears entirely because numeric comparison never touches the tz machinery. There is a test that fails if this is ever "simplified" to a field.
- **[views/year]**: `YearView` computed its data in the render body with no memoization, issuing **516** `getEventsForDateRange` calls per render (12 month queries + 12 x 42 mini-calendar day queries). Nothing caches beneath that call, so with the recurrence plugin every one re-expanded every RRULE — one recurring event cost ~316 ms per render, sixteen cost ~5.4 s. Memoizing the old shape would not have helped: all 516 ranges are distinct, so a range-keyed cache gets zero hits *within* a render, and the first paint is the problem. The fix is structural — one query for the visible span, then bucket by day. It now issues 3.
- **[utils/dayjs]**: The `startOf`/`endOf` patch re-derived the zone offset on every call via a `format()` plus a full `dayjs.tz()` reparse, ~81 µs once a default timezone is set. The offset is now memoised, keyed on the zone plus the result's **wall-clock minute** — not its instant, because during a transition a result may still carry a stale offset (the very case the patch exists to correct), so two results sharing an instant can legitimately need different answers. Verified behaviour-preserving across 292 104 comparisons over 13 zones including `Australia/Lord_Howe` (30-minute DST shift), `Pacific/Chatham` (+12:45), `Europe/Dublin` (negative DST) and `Asia/Kathmandu` (45-minute offset), zero mismatches. Worth knowing: this is the **least** impactful change in the series (~1.6x), not the most. Profiling the unpatched library shows `startOf('day')` at 352 ns on a plain instance versus 47 779 ns on a `.tz()` one — the cliff is dayjs-timezone's own, and the patch's lookup was only ~22 µs of ~81 µs. What actually fixed the timezone problem was moving tz-aware `startOf` out of the hot loops.

## Changes (PR #241 review round 2)

- **[utils/events]**: Fixed a second bug this branch introduced, and the more damaging of the two. Both the agenda and the year view walked days with `cursor.add(1, 'day')`, which carries the receiver's UTC offset forward. Once the walk crossed a spring-forward the cursor sat an hour past true local midnight while the loop bound came from `startOf('day')` and was normalised, so the comparison failed one iteration early and the range's **last day was dropped**. `main` was immune because `isSameOrBefore` goes through `startOf`, which this repo patches to re-derive the offset — replacing it with a numeric bound to avoid those calls also removed the normalisation that made the walk correct. Measured over 396 month windows across 11 zones and 2024-2026: 24 windows lost their final day. With `window="month"` in `Europe/London`, March 2025 rendered no group for the 31st at all. The walk now lives in one place, `collectDaysBetween`, and re-normalises after every step — one `startOf` per day, which is d calls, not d x n.
- **[views/year]**: Same defect in the year grid, which is one contiguous walk from January's grid start to December's. Ordinary DST zones hide it because the spring and autumn skews cancel by December; zones whose offset changes permanently mid-year do not (`Africa/Casablanca` 2018, `Europe/Volgograd` 2018, `Asia/Pyongyang` 2018, `Asia/Amman` 2022). The comment claiming the cursor "lands on `lastGridDay` exactly" was false and is gone.
- **[views/year]**: Corrected a second piece of false reasoning in a comment: it claimed `findDayIndex` returning -1 meant no clamping guard was needed, but `.at(-1)` reads the **last** element, so a negative index would have rendered the wrong cell rather than falling back. The cell lookup now guards on the index explicitly.
- **[utils/events]**: `bucketEventsByDay` and `countEventsByDay` were the same membership dispatch written twice, so malformed-input semantics had to be hand-synced. Both are now thin wrappers over `forEachEventDay`. That also removed a dead empty-index guard: with no days `getDaySpan` returns undefined and `getMalformedEventDays` returns `[]`, so nothing is visited — `countEventsByDay` never had the guard, which was the tell.
- **[utils/events]**: Noun-phrase helpers renamed to verb phrases: `dayIndexOf` → `findDayIndex`, `daySpanOf` → `getDaySpan`, `lastIndexAtOrBefore` → `findLastIndexAtOrBefore`, `firstIndexAtOrAfter` → `findFirstIndexAtOrAfter`, `malformedEventDays` → `getMalformedEventDays`. `getDaySpan`'s three-clause guard is now three named booleans, and the `?? Number.NaN` sentinel is lifted out of the binary-search comparisons, where a NaN would have flipped the branch silently.
- **[agenda]**: The grouping loop opened `if (!span)` inside `if (event.allDay)`. Each membership rule is now a named function returning day positions (`getAllDayPositions`, `getTimedPositions`) dispatched by `getEventDayPositions`, so the loop is flat and the reason the agenda cannot delegate to `bucketEventsByDay` sits at the point of dispatch.
- **[tests]**: `day-index.test.ts` named a module that does not exist — everything it imported came from `events.ts`, so that module had two test files with two builder sets. Folded into `events.test.ts` per the "never create new test files" rule. Also extracted `yearViewTree` in the query-count suite, where the provider block was copied three times.
- **[utils/dayjs]**: Narrowed an over-broad comment. "IANA offset transitions land on minute boundaries" was doing correctness-proof duty for minute-granularity cache keys but is only true for post-1970 civil transitions; the tz database can represent sub-minute offsets for older entries.

## Notes

Every new test was verified load-bearing by reverting the fix and re-running:
2 of the `collectDaysBetween` cases, all 3 agenda cases and all 4 year-view cases
fail against the un-normalised walk.

The year-view assertions took two attempts, and the first attempt is the
instructive one. Asserting on grid **shape** — 42 cells, distinct consecutive day
keys — passed against the bug, because a missing day falls through to
`monthGridStart.add(offset, 'day')` and recomputes the correct date. What does not
survive a short walk is the event **count**, which comes from the day index and
silently reads zero. A shape-only test would have been inert.

Both bugs in this branch came from the same trade: replacing a `startOf`-based
comparison with a numeric one to avoid the tz cost, without noticing that the
`startOf` was also doing the normalising. The lesson is narrower than "be careful
with DST" — when removing a call for performance, check what else it was doing.

`getMonthGridRange` in `date-utils.ts` has the same class of defect and is used by
the month view and calendar navigation. For `Europe/London` and `Europe/Berlin`,
April 2025 with `firstDayOfWeek: 1`, it returns 2025-03-24 where the correct grid
start is 2025-03-31 — a week early, so a whole week of days is missing from the
month grid. Left for its own change: it is a visible layout change and does not
belong in a performance PR. The divergence is recorded in a comment next to
`monthGridStartOf` so the two definitions are not silently inconsistent.
