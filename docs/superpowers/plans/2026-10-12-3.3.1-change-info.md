# 3.3.1 Change info (`delta`, `revert`) Implementation Plan

> **For agentic workers:** Implement task by task with TDD (superpowers:test-driven-development).
> Part of `docs/roadmap.md`, release 3.3, item 3.3.1.

**Goal:** Every `onEventsChange` call for an update says how far the event's start moved (`delta`),
and every call carries a `revert()` that undoes the whole action in the calendar's store.

**Architecture:** Both are computed in `features/calendar/hooks/calendar-data/event-changes.ts`,
the one place every mutation is reported from (`toRowChange` for plain rows, `dispatchMutationResult`
for plugin results). No new callback, no new prop.

**Tech stack:** TypeScript, React 19, configured dayjs from `@ilamy/utils/dayjs`, bun test, Playwright.

## The standard (verified at FullCalendar v7.1.1 source, tag `v7.1.1`)

Paths under `packages/preact/src/`.

- `eventChange` info is `{ oldEvent, event, relatedEvents, revert }` (`event-crud.ts:13-18`); `eventDrop`
  adds `delta` (`interaction-plugin/interactions/EventDragging.ts:289-301`). Docs: https://fullcalendar.io/docs/eventChange, https://fullcalendar.io/docs/eventDrop.
- `delta` is a Duration `{ years, months, days, milliseconds }` (`headless-calendar/src/duration.ts:25-31`)
  computed by `diffDayAndTime` (`headless-calendar/src/marker.ts:48-58`): `days` = difference of the two
  start-of-day dates, `milliseconds` = difference of the two **wall-clock** times of day. So a drag across a
  DST change keeps whole days and the event keeps its clock time.
- `revert()` restores the pre-action rows of every event the action touched (`EventDragging.ts:281-286`,
  `structs/event-store.ts:55-77`), by dispatching a store merge. It fires no change callback.

## Deliberate mapping (record it in docs; do not add duplicates)

- ilamy's `EventsChange.event` is already "the event the user acted on, as it was shown" — i.e. the
  **pre-change** event (`packages/types/src/index.ts:170-187`). That is FullCalendar's `oldEvent`. Do **not**
  add an `oldEvent` field; document the mapping in the field's TSDoc and in `docs/event-change-callback-design.md`.
- FullCalendar's `relatedEvents` is covered by `added`/`updated`/`deleted` (more precise). Not added.
- ilamy has one callback, so `delta` is present on every `update` (zero when the start did not move), not
  only on drags. `years`/`months` are omitted: no ilamy action produces them. Shape: `{ days, milliseconds }`.

## Global constraints

- No breaking change: existing fields and callbacks unchanged; `onEventUpdate/Add/Delete` untouched.
- Never import dayjs directly; use `@ilamy/utils/dayjs`. ISO strings in tests (`'2025-03-12T09:00:00.000Z'`).
- `.at()` not `[]`, no `!`, no `any`, named exports only, name every condition (CLAUDE.md Code Quality).
- Unit AND e2e tests written first; prove each by reverting the implementation and watching it fail.

## Interfaces

```ts
// packages/types/src/index.ts
/** How far an update moved an event's start, as FullCalendar's Duration: whole calendar days plus wall-clock time. */
export interface EventDelta {
	days: number
	milliseconds: number
}
export interface EventsChange {
	// existing fields unchanged
	/** For 'update': start moved by this much (zero if unchanged). Undefined for 'add' and 'delete'. */
	delta?: EventDelta
	/**
	 * Undo the whole action in the calendar's own store: removes `added`, restores the
	 * previous version of every row in `updated`, re-inserts `deleted`. Fires no callbacks
	 * (FullCalendar's revert does not either). A consumer that controls `events` reverts its own state instead.
	 */
	revert: () => void
}
```

Helper (in `event-changes.ts`, exported for its unit test):

```ts
export const toEventDelta = (before: Dayjs, after: Dayjs): EventDelta
```

`days` = `after.startOf('day').diff(before.startOf('day'), 'day')` (whole calendar days, in the calendar's zone);
`milliseconds` = wall-clock time of day of `after` minus that of `before`, from the clock fields
(`hour`, `minute`, `second`, `millisecond`), **not** from `diff` against midnight (which is off by an hour on a
DST day). Verify the `diff(..., 'day')` result is exact across a DST change with a test.

## Tests to write first

Unit (`event-changes.test.ts` and the mutation hook tests):

1. `toEventDelta`: same day +90 min → `{ days: 0, milliseconds: 5_400_000 }`; +1 day same time → `{ 1, 0 }`;
   −2 days −30 min → `{ -2, -1_800_000 }`; across midnight 23:00 → 01:00 next day → `{ 1, -79_200_000 }`.
2. DST: with zone `America/New_York`, 2025-03-08 10:00 local → 2025-03-09 10:00 local → `{ 1, 0 }`
   (machine-zone independent: run the test file once with `TZ=America/Vancouver bun test <file>` too and
   report the result).
3. updateEvent of a plain event moved 1 day → `onEventsChange` receives `delta { 1, 0 }`; title-only edit →
   `delta { 0, 0 }`; add and delete → `delta` undefined.
4. `revert` after add removes the row; after update restores the exact previous row object; after delete
   re-inserts the row; none of the three calls `onEventAdd/Update/Delete/EventsChange` again.
5. Recurring scopes (use the recurrence plugin through the public API as existing tests do): edit "this",
   "following" and "all" on a series with one moved occurrence, call `revert`, assert the stored rows
   deep-equal the rows before the action.
6. `revert` called after an unrelated later change (another event added) restores only this action's rows and
   keeps the later one.

e2e (`behaviour.spec.ts`, real pointer, existing drag helpers in `apps/e2e/tests/support/`):

7. Drag an event one day right and 30 minutes down in week view → the published change has
   `delta { days: 1, milliseconds: 1_800_000 }`.
8. With `&revertChanges=1`, drag an event → after drop the bar is back at its original geometry (compare
   bounding boxes before and after) and the published rows are unchanged.
9. Same as 8 in month view and in a horizontal resource view (cross-resource drag reverts the resource too).
