# 3.3.3 Event resize Implementation Plan

> **For agentic workers:** Implement task by task with TDD (superpowers:test-driven-development).
> Part of `docs/roadmap.md`, release 3.3, item 3.3.3. Closes kcsujeet/ilamy-calendar#93.

**Goal:** Users change an event's length by dragging its edge: the end edge always (when allowed), the
start edge with `eventResizableFromStart`. Works in every grid view, regular and resource, both orientations.

**Architecture:** A resize is a drag whose other end is pinned. The bar renders one small handle per
resizable edge; each handle is its own dnd-kit draggable with data `{ type: 'calendar-event-resize', edge }`.
The existing droppable cells already say which slot/day the pointer is over (`DropCellData`); a resize maps
that cell to a new end (or start) instead of moving the event. The existing drag preview, refusal path
(disabled cells, `eventAllow`, no preview + not-allowed cursor), drop commit (`useDropCommit`, scope dialog for
recurring events) and change reporting are reused. No second interaction system.

**Tech stack:** TypeScript, React 19, @dnd-kit/core, configured dayjs (`@ilamy/utils/dayjs`), bun test, Playwright.

## The standard (FullCalendar v7.1.1 source, tag `v7.1.1`, paths under `packages/preact/src/`)

- Handles: the end handle only on the segment with `isEnd`, the start handle only on the segment with
  `isStart` **and** `eventResizableFromStart` (default `false`) (`StandardEvent.tsx:95-96`). A bar split across
  rows/weeks therefore has at most one end handle.
- Gate: a handle exists only if the event is `durationEditable` (`StandardEvent.tsx:95-96`), resolved like
  `startEditable` (calendar `eventDurationEditable ?? editable`, event `durationEditable ?? editable`, event wins
  — `component-util/event-ui.ts:61-94`).
- Not resizable: list views; dot-style ("list-item") events in day grids, i.e. a single-day timed event in month
  view (`DayGridRow.tsx:527`, `daygrid/event-rendering.ts:13-26`). A multi-day timed event or an all-day event in
  a day grid is resizable.
- Confined: a resize stays within the component it started in — it cannot cross between the all-day row and the
  time grid (`interactions/interaction.ts:44-48`). Across week rows of one month grid is fine (one component).
- Snap: time grid by `snapDuration || slotDuration` (ilamy has only `slotDuration` until 3.3.5; use it); day grids
  by whole days, keeping a timed block's time of day (`TimeGridCols.tsx:113,162-172`).
- Minimum: no explicit minimum; a mutation that would put end ≤ start is null (no change, and — unlike a refusal —
  no not-allowed cursor) (`EventResizing.ts:249-300`). In practice the minimum is one snap unit.
- Validation: the same validator as drag, including `eventAllow`, with the resized range (`EventResizing.ts:150`).
- Report: `eventResize` info carries `startDelta` and `endDelta` (`EventResizing.ts:222-229`).
- Touch: FullCalendar only resizes an already-selected event on touch (`EventResizing.ts:86-88`). ilamy has no
  event selection; see Deviations.

## Deviations (record in TSDoc and docs; justify)

1. **No separate `onEventResize` callback.** ilamy reports every action once through `onEventsChange` (#309). Add
   `endDelta?: EventDelta` to `EventsChange` (on every `update`, like `delta`; FullCalendar's `startDelta` is our
   existing `delta`). One callback, no duplicate API. Update `docs/roadmap.md`'s 3.3.3 row to say so.
2. **Touch:** no resize on touch-only devices until event selection exists (roadmap 4.1.3). FullCalendar only
   resizes an already-selected event on touch (`EventResizing.ts:86-88`), and a 6px handle took taps and
   long-presses ~10px away (Chrome touch hit-test retargeting). The handles are hidden under
   `@media (hover: none)`, so touch taps and moves behave as before 3.3.3. (An earlier version of this plan
   resized on long-press; QA showed it cost taps and moves on short bars.)

## API

```ts
// IlamyCalendarProps
/** Events can be resized. @default editable */
eventDurationEditable?: boolean
/** Also show a handle on the start edge. @default false */
eventResizableFromStart?: boolean
// CalendarEvent
durationEditable?: boolean
// EventsChange
/** For 'update': how far the event's end moved (zero when it did not). */
endDelta?: EventDelta
```

`resolveStartEditable` (in `features/calendar/utils/resolve-editability.ts`, added by 3.3.2) gets a sibling
`resolveDurationEditable` with the same precedence. Keep both tiny and pure.

## Behaviour details

- End edge, time grid: new end = end of the hovered slot (exclusive). Day grid / all-day: new end = start of the
  day after the hovered day (exclusive end, RFC 5545 DTEND; #248), keeping the time of day for a timed block.
  Start edge mirrors it (new start = start of hovered slot / day).
- If the hovered cell would make end ≤ start, the preview stays at the minimum (one slot / one day) — do not flip
  the event. (FullCalendar returns null; showing the clamped minimum is equivalent visually only if it equals the
  original; implement the FullCalendar way: null mutation → preview shows the original, no cursor change.)
- Hovering a cell of the other component (all-day row while resizing in the time grid, or vice versa) is ignored
  (keep the last valid preview), not refused.
- Resource views: a resize never changes the resource; hovering another resource's lane maps to the same time on
  the event's own resource.
- Cursor on the handle: `ns-resize` in vertical time grids, `ew-resize` in horizontal ones (day grids, horizontal
  resource timeline). Handles must not steal clicks: a click on the bar body still opens the event.
- Accessibility: handles are pointer affordances; give them `aria-hidden` (keyboard resize is roadmap 4.3.6).
- A recurring occurrence routes through the plugin's scope dialog exactly like a drop (`useDropCommit`).

## Tests to write first

Unit:
1. `calculateResizeTimes`: end edge in a time grid at 15/30/60-minute slots; end edge in a day grid for an all-day
   event and for a multi-day timed block (time kept); start edge both; end ≤ start → null; across a DST day
   (America/New_York, 9 Mar 2025) the new end is the hovered slot's wall-clock end; month resize across a week row.
2. `resolveDurationEditable` truth table (mirror the start one).
3. Handle rendering: end handle only on the `isEnd` segment; start handle only with `eventResizableFromStart` and
   `isStart`; no handles when not durationEditable, in the agenda, or on a single-day timed event in month view.
4. `endDelta`: +30 min resize → `{ days: 0, milliseconds: 1_800_000 }`, `delta` zero; start-edge resize → `delta`
   set, `endDelta` zero.
5. `eventAllow` receives the resized range and can refuse it.

e2e (`apps/e2e/tests/drag.spec.ts` new `describe('resize')`, real pointer; add `eventResizableFromStart` and
`eventDurationEditable` query params in `apps/e2e/src/harness-config.ts`):
6. Week view: drag the bottom handle down two slots → event ends 1 h later; the published change has
   `endDelta { 0, 3_600_000 }`.
7. Month view: drag an all-day event's end handle two days right (and onto the next week row) → ends 2 days later.
8. Horizontal resource day and vertical resource week: resize keeps the resource.
9. `eventResizableFromStart=true`: drag the top handle up → starts earlier; without the flag there is no top handle.
10. `eventDurationEditable=false`: no handles; a per-event `durationEditable:false` in the `edit-permissions`
    scenario has no handle while its neighbour does.
11. `eventAllow=no-weekends`: resizing an all-day event onto Saturday shows the not-allowed cursor and commits
    nothing.
12. Recurring: resizing an occurrence opens the scope dialog; choosing "this" resizes only it.
13. Shrinking past the start keeps the event at its original length (no flip, nothing committed).
14. A click on the bar body still opens the event (handles do not swallow it).

## Global constraints

No breaking change; never import dayjs directly; `.at()`, no `!`, no `any`, named exports, name every condition;
unit AND e2e first; revert proof (disable handle rendering, `calculateResizeTimes`, and the `eventAllow` check on
resize → named tests fail). Public text never frames this as parity with another library; citing FullCalendar
for a specific behaviour with file:line is fine. Do not write the dev log or CHANGELOG.
