# Development Log - 2026-08-12

## Changes

- **[utils/dayjs]**: Fixed #247 — the configured `dayjs()` constructor discarded the offset on ISO strings, so in any non-UTC zone every event landed at the wrong instant, often on the wrong day. The wrapper aliased the constructor to `dayjs.tz(input)`, and the tz plugin reads a **string** as wall-clock time in the target zone ([docs](https://day.js.org/docs/en/plugin/timezone)) while converting Date/number/Dayjs as instants. In Europe/Vienna `dayjs('2026-08-17T22:00:00.000Z')` therefore yielded `2026-08-17T22:00+02:00` instead of `2026-08-18T00:00+02:00`, which is why the reporter's `new Date(value)` workaround behaved correctly.

- **[utils/dayjs]**: The constructor now branches on what a string actually means, because the two kinds mean different things and only one of them has an instant. A string carrying `Z`/`±HH:MM`/`±HHMM` keeps its instant and merely renders in the configured zone; a string carrying none (`'2026-03-02'`, `'2026-03-02T09:00'`) is anchored in the configured zone via `dayjs.tz()`. Both rules exist to say the same thing: **the machine's zone never decides anything the `timezone` prop can decide**. Reading offset-less strings locally (the first cut of this fix) would have put the same calendar on a different instant for every user. Offset detection matches the TIME half only, so the hyphens in `2026-03-02` cannot pass for an offset; dayjs's own parse regex has no offset group, so these strings fall through to the native `Date` parser, which accepts `Z`, `±HH:MM` and `±HHMM` but rejects a bare `±HH`.

- **[utils/dayjs]**: The constructor short-circuits on an invalid input before `dayjs.tz()` can see it. `dayjs.tz()` throws `RangeError: date value is not finite` from inside the plugin rather than returning an invalid instance, a latent crash reachable through `safeDate('garbage')` whenever a timezone was configured. Also, a second constructor argument is now ignored rather than misread as a zone name (#242's runtime `RangeError`); the `@ts-expect-error`-checked type is the remaining guard, which is what #242 actually wanted.

- **[calendar/timezone ordering]**: The `timezone` prop never applied on mount. The engine's effect was guarded by `timezone !== lastTimezoneProp.current` with the ref **initialized to the prop**, so the guard was false on the mount render and `dayjs.tz.setDefault` never ran at all — the zone only took effect if the prop later changed. Seeding the ref with `undefined` fixes it, and the effect's existing conversion is what moves the dates the first render already resolved onto the calendar's clock. A `<IlamyCalendar timezone="Asia/Tokyo">` showing a `12:00Z` event settled at `12:00 +00:00`; it now settles at `21:00 +09:00`.

- **[calendar/timezone ordering]**: Considered and rejected applying the zone during render (via a `useCalendarTimezone` hook, which is why one appears in this branch's history). It is correct on the very first paint, but `dayjs.tz.setDefault` is a module-global write and Next.js prerenders `'use client'` components on the server ([docs](https://nextjs.org/docs/app/getting-started/server-and-client-components)), so a multi-tenant server prerendering two zones concurrently could interleave them. Effects never run during SSR, so the write stays in an effect. The accepted cost is one extra render and a first paint on the machine's clock.

- **[calendar/timezone ordering]**: Dropping the `timezone` prop now returns the calendar to the machine's zone instead of stranding it: `setDefault(undefined)` for fresh parses, and the conversion effect lost its `timezone &&` guard so held dates convert in both directions (`date.local()` when the prop is gone).

- **[calendar/normalization]**: `normalizeEvents` and the navigation slice's initial date no longer pass an already-Dayjs value straight through. A consumer builds those in its own module, in the machine's zone, so passing them through rendered a correct instant against the wrong clock. Routing them back through the configured constructor keeps the instant and moves only the clock.

- **[drag-to-create/read-cell]**: Comment only. Its `dayjs.utc(iso).tz(timezone)` no longer needs to justify itself as a workaround for the constructor. Kept as-is rather than collapsed to the bare constructor: parsing explicitly means the reconstruction depends only on its arguments, not on whatever zone `dayjs.tz.setDefault` last received.

- **[docs]**: `docs/configured-dayjs-timezone-bug.md` was the 2026-06-21 analysis of this exact bug, filed as "documented, not yet fixed" and recommending "fix option 1: make the configured constructor detect a zone-carrying string". That is what shipped, so the file was renamed to `docs/timezones.md` and rewritten as the contract reference rather than a bug report: what anchors each input shape, why the zone is applied during render, how incoming props are re-anchored, and the four rules for writing an honest timezone test. Linked from `AGENTS.md` (Key Paths + a Dates rule), `docs/testing-guide.md` and `docs/time-grid.md`.

- **[tests/DRY]**: The timezone tests repeated the same `renderHook(() => useCalendarEngine({ ...defaultConfig, events, initialDate, timezone }))` five times. Replaced with a `renderZonedEngineHook(timezone, events?)` helper following the repo's `render<MeaningfulName>Hook` convention: it returns the clocks under test (`currentDate`, `firstEventStart`) plus `moveTo(zone)` for the rerender, so each test reads as "mount in a zone, move, read a clock". The dayjs tests grew a `parsedIn(zone, value)` helper for the same reason.

## Notes

**Why 1127 tests never caught this.** happy-dom's `GlobalRegistrator` makes `Intl` resolve to UTC (`process.env.TZ` is unset, the resolved zone is `UTC`), and at offset zero the wall-clock misreading is a no-op. Assertions that both parse and render through the same broken constructor cancel out. New timezone tests must set an explicit `setDefault` zone and assert `toISOString()`/`valueOf()` at least once, so a shifted instant cannot hide behind a matching format.

**A test cannot vary the machine's zone.** dayjs's timezone plugin caches an `Intl.DateTimeFormat` per zone key, so mutating `process.env.TZ` mid-run is ignored once that formatter exists — the first zone used wins for the rest of the process. An early draft of the dayjs tests used a `parseInMachineZone` helper that looked like it proved machine-independence and proved nothing; it was replaced with absolute-instant expectations that hold in any zone (verified under America/Vancouver, UTC and Asia/Kolkata).

**Running the suite with an exported `TZ` now fails more, on purpose.** Under `TZ=Asia/Kolkata` the suite fails 59 tests against main's 10. The added failures are tests that hard-code UTC-shaped display, e.g. a `09:00Z` event asserted at `top: 0%` of a 9am business band; with the fix an IST viewer correctly sees it at 14:30 (`top: 68.75%`). The old behavior made the rendered clock face identical in every zone, which is precisely the bug. CI and default local runs resolve to UTC and are unaffected. If we want local runs zone-proof, the one-line fix is pinning `process.env.TZ = 'UTC'` in each package's `happydom.ts` preload — not done here, since it is test-infra policy rather than part of this fix.

**`safeDate` keeps its `isDayjs` pass-through.** An earlier cut of this change removed it for symmetry with `normalizeEvents`, which was wrong on three counts: the only call site that can pass a Dayjs (`IlamyCalendar`'s `initialDate`) is re-anchored downstream by the navigation slice, the other (`safeDate(e.recurrenceId)`) takes a `string` so the branch is unreachable, and removing it silently turned an invalid Dayjs from a pass-through into `undefined` with no test covering it. The navigation slice's own `isDayjs` check was the opposite case and was right to remove: `initialDate` is TYPED as Dayjs there, so the check could only ever choose pass-through, and nothing downstream re-parses it — reinstating it fails two engine tests.

**Process note.** Three changes in this branch were made before their context was read, and two were reverted as a result: the recurrence date-picker was churned twice before the constructor's final shape settled, and `safeDate`'s `isDayjs` pass-through was removed for symmetry when it was redundant. `docs/performance.md` documents the very effect that was rewritten here and was not read first; `.agents/commands/load-context.md` and `packages/plugins/recurrence/src/utils/recurrence-timezone.test.ts` were also found late. Read `docs/timezones.md` + `docs/performance.md` together before changing anything in this area, and run `/load-context` at session start.
