# Development Log - 2026-08-21

## Changes

Performance work on the event/date layer, taking the diagnosis from #241 and its
linked issue #245 but implementing it differently. All figures re-measured on
this machine rather than copied from that PR.

**The root cause is one thing, and it is not our code.** Every dayjs comparator
routes through `startOf` (`isBefore` -> `endOf(units)`; `isSame` -> both
`startOf` and `endOf`; `isSameOrAfter` = `isSame || isAfter`, so up to three).
dayjs-timezone overrides `startOf` with a format -> reparse -> `.tz(zone, true)`
round-trip that runs on EVERY call, including the no-op `startOf(undefined)`.
Verified in `node_modules/dayjs/esm/index.js` and
`esm/plugin/timezone/index.js`.

That re-anchor also MOVES an instance whose UTC offset is stale, which `add()`
produces across a DST transition, so two instants an hour apart compared equal.
Both halves are open upstream: dayjs#1399 (correctness, 2021) and dayjs#2344
(performance, 2023). Neither identifies the cause.

- **[utils/dayjs]**: new `compareByInstant` plugin. `isBefore`, `isAfter`,
  `isSame`, `isSameOrBefore` and `isSameOrAfter` answer by epoch millisecond
  when no unit is given AND the operand is already a Dayjs, which is what dayjs
  documents unitless comparison to be ("default milliseconds"). A unit asks a
  different question and any other operand needs dayjs's coercion; both fall
  through untouched. Extended last, so it wraps the plugin-installed
  comparators.

  `America/New_York`: `isBefore` 44 957 -> 10 ns, `isSameOrAfter`
  134 739 -> 13 ns, `isSame` 64 794 -> 13 ns. Fallbacks unchanged:
  `isSame(x, 'day')` 101 684 ns, `isBefore('2025-01-01')` 49 282 ns.

- **[utils/helpers]**: `dayKey` and `isSameDay`. These are the ONE comparison
  worth keeping our own: `isSame(x, 'day')` carries a unit, so it still routes
  through dayjs-timezone's `startOf` at ~101µs, and every grid cell asks it.
  Rendered keys answer for ~1.5µs. `overlapsRange` is unchanged from `main`.

- **[calendar/date-utils]**: `isToday` uses `isSameDay`. `getDayKey` is gone
  entirely rather than re-exported: it was a second name for `dayKey`, so the
  eight call sites now import `dayKey` from `@ilamy/utils/helpers` directly and
  its two tests moved with it.

- **[agenda]**: `AgendaDayGroup` had its own inline
  `group.date.isSame(dayjs(), 'day')`, a private copy of the core's `isToday`.
  Now calls the shared `isSameDay`.

- **[calendar/year-view]**: one query for the visible year instead of 516 per
  render (12 month ranges + 12 x 42 mini-calendar days), computed in the render
  body with no memoization. The win is 516 queries per render down to one per
  render, NOT memoization across renders: `getEventsForDateRange` takes a new
  identity on every render (three distinct identities over five renders,
  measured), so the `useMemo` recomputes each time. Stabilising that is the
  pre-existing provider identity churn noted on #241 and is out of scope here. Observed through a plugin's `transformEvents` the
  count was **1034** (517 x two render passes); it is now **4**, pinned with
  `toBe`. Memoizing the old shape would not have helped: all 516 ranges are
  distinct, so a range-keyed cache gets no hits within a render. Cell and badge
  counts are re-derived from the single list with the same predicate. Month
  badges count distinct events rather than summing day buckets, which would
  count a five-day event five times.

- **[deps]**: dayjs 1.11.21 -> 1.11.23 across all five packages that declare it
  (two timezone-plugin fixes: dayjs#3174 and dayjs#3180). Dropped the unused
  `isBetween` plugin: zero references anywhere, tests included.

## Notes

**This change was twice as large before it was right.** The first version added
numeric comparators to `@ilamy/utils/helpers` and rewrote every hot call site to
use them: the agenda's `appearsOnDay` and day loop, `layout/vertical.ts`,
`layout/horizontal.ts`, the recurrence override lookup, `overlapsRange` itself.
Once `compareByInstant` existed, all of it was redundant. `overlapsRange` measures
124ns using plain dayjs comparators against 99ns using hand-rolled ones, with zero
disagreements across 49 boundary cases. Fixing the layer that was actually broken
removed the need to touch any of those files, and with them went the riskiest
edits: see the DST cursor note below.

**Tests for the comparator patch were written before the flip, deliberately.** An
earlier prototype passed all 1 195 tests while silently changing `isSame` from
true to false on drifted instances. That is exactly the shape
`.agents/rules/change-impact.md` warns about: behaviour nobody had pinned. Two of
the six new cases fail against the old implementation.

**A DST regression that no longer exists.** While rewriting the agenda loop, the
first version removed `cursor.startOf('day')` as apparently dead work, since the
cursor is already a start-of-day. It is not: `add(1, 'day')` on a tz-aware
instance holds the wall clock at 00:00 but carries the PREVIOUS UTC offset across
a transition, so the day after a spring-forward is emitted as `00:00 -05:00`
(05:00Z) when true local midnight is 04:00Z, and an event in that missing hour
lands in the previous day's bucket. Verified against `main`, which passes all
fourteen cases, so it was ours. The file is now untouched, so the bug cannot
occur, but the five timezone/DST tests are kept: no suite covered agenda grouping
under a timezone, and that gap was real.

**`monthDate.endOf('month')` inside a filter predicate** was re-evaluated once per
event: 512 x 12 x ~45µs. That one misplaced call was ~760 ms of an 848 ms loop,
invisible to tests. It is hoisted.

**`fixTimezoneOffset` CANNOT be deleted.** That was the hope behind the upgrade,
since dayjs#3169's root cause ("both `new Date(target)` and `getTimezoneOffset()`
depend on the host") is the same family as the bug our patch works around. Tested
against raw upstream 1.11.23 with no patch: walking all 365 days of 2025 in six
zones, calling `startOf('day')` and `endOf('day')` and checking the reported
offset against `Intl`, 4 380 checks produced 4 mismatches on hosts UTC /
Europe/Paris / Europe/London and 12 on America/New_York, always on a DST
transition day. With the patch: 0 on every host tried.

**Behaviour changes worth a changelog line.** Dropping `isBetween` means a
consumer calling `.isBetween()` on the `dayjs` exported from the Plugin SDK will
throw. Unitless comparison now answers by instant, so a Dayjs carrying a stale
offset compares differently; the new answer matches dayjs's documented contract.
That reaches `dayjs.max`/`dayjs.min` too, since the minMax plugin calls
`isAfter`/`isBefore` with no unit. And because `dayjs.extend` mutates the
prototype of whichever `dayjs` module instance resolves, an app whose own dayjs
dedupes to the same copy inherits all of it outside the calendar. The contract
is written up in `docs/timezones.md` under "Comparing dates".

**`isSameDay` is not a drop-in for `isSame(x, 'day')`.** It renders each operand
in its own zone, so two instances anchored in different zones disagree with
dayjs on the same instant (New York 23:00 vs Tokyo 12:00 the next day: dayjs
says true, this says false). Every call site passes operands already in the
configured zone, and a test pins the difference so it stays a contract rather
than a surprise.

**The year-view cells keep their un-normalized `dayDate`.** After a fall-back the
cell's label, click target and event window all derive from the same skewed
instant and agree with each other. #241 noted the resulting one-hour window skew
as a separate, smaller defect; normalizing only some of those derivations is what
shifted its grid by a whole day.

**Remaining floor.** The year view still spends ~72 ms on 504 tz-aware
`startOf`/`endOf` pairs. `main` paid that too, so it is not a regression, and it
is inherent to dayjs-timezone. Numeric geometry in `layoutHorizontal` /
`layoutVertical` and virtualization remain unmeasured and out of scope.
