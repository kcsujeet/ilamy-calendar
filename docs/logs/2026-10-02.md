# Development Log - 2026-10-02

## Changes

- **[vertical grid navigation]** (#300): Moving a week in a vertical time grid no longer remounts every cell, which made a 15-minute resource week take seconds to navigate.
  - Cause, from a CPU profile of three week navigations: about half the time was `DroppableContainersMap` in `@dnd-kit/core`. Every `RegisterDroppable` and `UnregisterDroppable` copies the whole container map (`core.esm.js:2628`, `:2673`, v6.3.1), so N droppables cost O(N²) to register.
  - Navigation paid it twice. The column keys and the cell keys inside a column both carried the column id, which carries the date, so React remounted all cells. The droppable id carried the date too, and `useDroppable` re-registers when its id changes (`useEffect(..., [id])`), so even a kept cell re-registered.
  - Fix: column and cell keys are positional, and `DroppableCell` takes its droppable id from `useId()`. The drop still reads the date from `data`, which `useDroppable` keeps in a ref refreshed every render (`useLatestValue`).
- **[keys]**: Removed `keys.droppable.dayCell` and the `id` prop of `DroppableCell`; nothing reads a droppable id other than dnd-kit itself.

- **[published types]** (#302): the shipped declarations referenced `dayjs.Dayjs3`, `dayjs.ManipulateType3` and `React.ReactNode3`, none of which exist, so a consumer type-checking with `skipLibCheck: false` failed.
  - Cause: bunup's declaration bundler (`@bunup/dts` 0.14.53, latest; `bunup` 0.16.32, latest) renames a local type on a name clash, and also renamed the matching member of a qualified name. `export type Dayjs = dayjs.Dayjs` became `type Dayjs3 = dayjs.Dayjs3`. Which qualified names get hit depends on clashes anywhere in the bundle, so it is not one line.
  - Fix: exported types use named type imports instead of qualified names: the dayjs aliases and `ConfiguredDayjs` (`utils/src/dayjs.ts`), and `ReactNode`/`Context`/`FC` in the calendar props, context and provider. The bundler now emits `type Dayjs3 = DayjsInstance` from `import { Dayjs as DayjsInstance } from "dayjs"`, which is valid.
  - The reporter also asked for a check against the generated types: `check:dist-types` runs a strict `tsc` (`packages/calendar/tsconfig.dist.json`, standalone, no `paths`) over `dist/**/*.d.ts`. Added to CI after the build, to the root `ci` script, and to `release`/`release:dry` before publishing.
  - Red first: the check failed with 7 errors on `c636da8`, the six the reporter listed plus one they missed (`React3.ReactNode3` in `dist/testing/index.d.ts`). Green after the fix.

- **[performance, non-breaking]**: five changes from a four-area profiling pass (recurrence, drag, context fan-out, per-cell work). Everything that would change public API, the cell DOM contract, event ids, plugin hook inputs, visuals or SSR was set aside. Headlines re-measured on production builds of apps/e2e (6 rooms, Chromium, median of 5), each prototype against `main`:
  - Recurring events, week view, 200 series started in 2015: "Next" 4,560 -> 188 ms.
  - Horizontal resource week, Asia/Tokyo: "Next" 194 -> 64 ms; vertical 15-min resource week 94 -> 79 ms.
  - Drag, script per pointer move: 16.2 -> 10.1 ms.
  - Drop (an event update): 141 -> 114 ms; the context change mostly removes re-renders (one event update: 18,178 -> 1,967 renders, 6-room 15-min week).
- **[recurrence]** `generateRecurringEvents` keeps a per-series memo (WeakMap on the event object, invalidated when its `rrule`, `start` or floating UNTIL changes): one rrule `between()` over the range plus 6 weeks either side, filtered the way `between()` filters, so a series that began years ago is no longer re-walked from DTSTART per column; `fromFloatingDate` results memoized (capped at 4096 per series); overrides matched through a set of instants (`isSame` with no unit compares instants). Cost: up to ~26 MB more heap in year view (measured by the profiling agent).
  - Considered and rejected: adding the default timezone to the memo key. Not needed: a `timezone` prop change rebuilds every event object (`use-calendar-engine.ts`, the timezone effect maps `currentEvents` to new objects in the new zone), so the memo's WeakMap key changes with it; and a given event object's expansion does not depend on the default zone anyway (measured identical with and without the memo across New York, London and Sydney DST changes). An earlier draft of this entry claimed the event objects survive a zone change; that was wrong (caught in review) and the test written on that premise is replaced by tests that change the rule and the start on the same object.
- **[cells]** A cell builds its default test id only when none is passed (the time grid always passes one), and `useProcessedWeekEvents` skips the two zone conversions per column when a row has no events.
- **[drag]** `pointerWithinLazily` replaces dnd-kit's `pointerWithin` as collision detection: the same inclusive point-in-rect test (`isPointWithinRect`, core.esm.js, v6.3.1), but it stops reading a cell's edges once one rules it out, then hands the survivors to `pointerWithin` itself, so hits and ranking are identical.
- **[context]**
  - dnd-kit sensor options are module constants: `useSensor` memoizes on the options' identity, so inline literals rebuilt dnd-kit's context and re-rendered every droppable on any render.
  - `useLatestHandler`: consumer event handlers (`onEventAdd/Update/Delete`, `onDateChange`, `onViewChange`, `onEventClick`, `onCellClick`, `onMoreEventsClick`) get a stable identity that calls the newest handler, `undefined` when absent. It writes its ref in `useInsertionEffect` because that runs before every layout effect, so a child's effect never reaches the previous handler (React documents the hook for CSS-in-JS; `useEffectEvent` is ruled out because Effect Events must not be passed to children or called from event handlers, https://react.dev/reference/react/useEffectEvent). Render-time callbacks (`getCellClassName`, `isCellDisabled`, `renderEvent`) are deliberately not wrapped.
  - Cells read `CalendarCellContext`, a memoized subset (date, view, spacing, business hours, cell callbacks and flags); the event-reading part of a cell is its own `GridCellEvents`, so time slots never read events. Cells now re-run `getCellClassName`/`isCellDisabled` when their inputs change rather than on every context change; pure callbacks are unaffected.
  - `docs/hooks-and-context.md` claimed the selector form avoided re-renders; it does not (plain `useContext`). Corrected.
- **[recurring e2e]** New `recurring` harness scenario (a 2015 Monday/Wednesday series and a daily stand-up, `plugins=recurrence`): this week's occurrences of the old series, and the same bars after navigating away and back. The round-trip spec first failed on `main` too: it measured bars mid slide-in; it now waits for animations.
- Set aside as possibly breaking: per-column event maps for the horizontal week (changes the range a plugin's `transformEvents` receives), a drag-preview store (a consumer's own draggable would stop tinting cells), building columns from one view-wide expansion (changes instance ids), applying the timezone during render (SSR). Found along the way: recurring events shift an hour after a DST change (#307), to be fixed separately.
- Fallow flagged `useCalendarEngine`'s cognitive complexity after the handler wrapping; the seven wraps moved into `useStableConfigHandlers`.
