# Development Log - 2026-08-13

## Changes

- **[calendar/event-form]**: Fixed #248 Part A — the form dropped nothing and kept everything, which is the wrong way round: it set hour and minute but left seconds and milliseconds untouched, so residue rode into stored events. Both builders now go through one `atMinute(date, time)` helper that ends with `.second(0).millisecond(0)`. The residue's source is the **+ New** path: `openEventForm()` with no arguments seeds `start` from `currentDate`, which originates in `dayjs()` and therefore carries the wall-clock seconds of page load, while an End Date picked from the calendar arrives clean at `00:00:00.000`. Mixing the two made a "12:00 AM to next-day 12:00 AM" event 23:59:27 long instead of 24h.

- **[calendar/interaction]**: `openEventForm` truncates its draft start to the minute for the same reason. This is not redundant with the builders: a consumer using `renderEventForm` receives `selectedEvent` directly and can save it without ever passing through them, and `openEventForm` is public API through the context. An explicitly passed `end` is left alone, since that is the caller's own value (a day cell deliberately passes `endOf('day')`).

- **[tests]**: Six new cases. Four pin that both builders clear seconds and milliseconds (timed and all-day paths), one pins the midnight-to-midnight duration at exactly 86,400s, one pins the seeded draft on a whole minute. The duration case is asserted as a **duration, not a column count**, deliberately: the column count is what #248 Part B changes, so pinning spans here would have to be rewritten by that work.

## Notes

**Why this looked like a prod-only ghost.** The symptom was that identical events spanned different numbers of days: May 11 to May 12 and May 19 to May 20 rendered as two-day bars while May 13 to May 14 rendered as one. `layoutHorizontal` classifies multi-day with `end.diff(start, 'day') > 0`, and dayjs truncates, so 23:59:27 becomes `0` and the event takes the single-column path. Whether an event was affected depended on **the second at which the page loaded** and on whether the user picked the start date from the calendar (clean) or accepted the seeded one (dirty). Reproducing it required driving the real form; hand-constructed events are always clean, which is why several rounds of probing missed it.

**Why the existing tests never caught it.** Every case in `event-form-utils.test.ts` passed `new Date('2025-01-15T00:00:00.000Z')`, already clean. The new `dirtyDate` fixture is the whole point.

**Scope check, done before editing.** A sweep for `\.hour(...)\.minute(` found four other call sites. `droppable-cell.tsx` and `dnd-utils.ts` both build from cell dates, and those are clean at the source (`getDayHours` already ends with `.second(0).millisecond(0)`, day cells derive from `startOf('week')`/`startOf('day')`), so they need nothing. The playground seed uses `dayjs().startOf('month')`, also clean. `date-utils.ts:94` was the existing precedent for the normalization pattern used here.

**Still open on #248**: Part B, the inclusive-versus-exclusive `end` convention across the layout, the all-day `23:59` storage, the iCal export and `eventOverlapsRange`. That is the breaking half and needs the multi-day span tests that still do not exist.
