# Development Log - 2026-08-21

## Changes

Performance work on the event/date layer, taking the diagnosis from #241 (and
its linked issue #245) but implementing it differently. The measurements below
were re-taken on this machine rather than copied from that PR.

The whole problem has one shape. `valueOf()` and `format()` are flat, immune to
the `timezone` prop; every dayjs **comparison** and every `startOf`/`endOf`
falls off a cliff once one is set. So the rule is: inside a loop, compare
epoch millis, and touch dayjs only at the boundaries.

| primitive | tz cleared | tz set |
|---|---|---|
| `.valueOf()` | 4 ns | 5 ns |
| `.format('YYYY-MM-DD')` | 837 ns | 727 ns |
| `.startOf('day')` | 2 416 ns | 45 821 ns |
| `.isSameOrAfter(x)` | 794 ns | 134 739 ns |
| `.isSame(x, 'day')` | 5 241 ns | 91 302 ns |
| `overlapsRange()` before | 2 922 ns | 457 820 ns |
| `overlapsRange()` after | 19 ns | 17 ns |

- **[utils]**: One documented home for the comparison rule, in
  `@ilamy/utils/helpers`: `isSameOrAfter`, `isSameOrBefore`, `isBefore`,
  `isAfter`, `isSame`, `isBetweenInclusive`, plus `dayKey` / `isSameDay`
  for calendar-day questions. Each names its dayjs equivalent, and a single
  block above them explains why they exist so the reasoning is not re-litigated
  in a comment at every call site. The unit-ed forms (`isBefore(x, 'month')`)
  ask a different question and are explicitly left alone.

- **[utils]**: `overlapsRange` compares epoch millis. dayjs's unitless
  comparators are *defined* as `valueOf()` comparisons, so this is the same
  function, but each one re-coerces its argument through the configured
  constructor (~29µs under a timezone). The three clauses are kept rather than
  collapsed to `start <= rangeEnd && end >= rangeStart`; those disagree on an
  interval whose end precedes its start, now pinned by two tests. Because the
  core, agenda and recurrence all route through this one helper since #248's
  follow-up, this single edit fixes every per-day filter at once.

- **[agenda]**: `appearsOnDay`'s timed branch is `isBetweenInclusive`, and
  `groupEventsByDay`'s loop condition is `isSameOrBefore`. The day cursor is now
  re-normalized each step with `.startOf('day')`.

- **[agenda]**: `AgendaDayGroup` had its own inline `group.date.isSame(dayjs(),
  'day')`, a private copy of the core's `isToday`. It now calls the shared
  `isSameDay`, which is both the perf fix and the deduplication.

- **[layout]**: `vertical.ts`'s cluster boundary and `horizontal.ts`'s
  multi-unit / truncation checks use the shared comparators. These run once per
  event during layout. The `startOf(gridType)` calls around them are unchanged:
  only the comparison moved.

- **[recurrence]**: the override lookup inside the occurrence loop uses
  `isSame`, so its cost is no longer occurrences x overrides x ~91µs.

- **[calendar/date-utils]**: `isToday` compares day keys instead of calling
  `isSame(now, 'day')`. Same answer, ~91µs to ~1.5µs.

- **[calendar/year-view]**: one query for the visible year instead of 516 per
  render (12 month ranges + 12 x 42 mini-calendar days), all computed in the
  render body with no memoization. Observed through a plugin's
  `transformEvents` the count was **1034** (517 x two render passes); it is now
  **4**. Memoizing the old shape would not have helped: all 516 ranges are
  distinct, so a range-keyed cache gets no hits within a render. Cell and badge
  counts are re-derived from the single list with the same predicate, so the
  numbers are unchanged. Month badges count distinct events rather than summing
  day buckets, which would count a five-day event five times.

## Notes

**Two regressions were introduced and caught during the work, both worth
recording because neither was visible to the suite as it stood.**

Removing `cursor.startOf('day')` from the agenda loop looked like dead work:
the cursor is already a start-of-day. It is not. `add(1, 'day')` on a
tz-aware instance holds the wall clock at 00:00 but carries the PREVIOUS UTC
offset across a transition, so the day after a spring-forward is emitted as
`00:00 -05:00` (05:00Z) when true local midnight is 04:00Z, and an event in
that missing hour lands in the previous day's bucket. The deleted call had
been silently repairing this every iteration. Verified against `main`: `main`
passes all fourteen cases, so this was ours, not pre-existing.

In the year view, `monthDate.endOf('month')` was written inside the filter
predicate, so it was re-evaluated once per event: 512 events x 12 months x
~45µs. That one misplaced call was **~760 ms** of an 848 ms loop, and no test
could see it. Hoisting it is the whole difference between 848 ms and 85 ms.

**What was deliberately NOT done**, versus #241's approach: no
`@ilamy/utils/events` module, no `WeakMap` bounds cache, no
`buildDayIndex`/`daySpanOf` binary search, no memoization of the dayjs DST
offset check. The cache exists in that PR to avoid recomputing `startMs`, but
`valueOf()` costs 4ns, so there is nothing to cache; and #241 predates the
#248 follow-up that gave the three overlap copies a single home, which is what
makes one edit sufficient here. Its two review regressions (gapped day lists,
year-view DST grid shift) both came from the index it introduced, so avoiding
the index avoids that class.

**The year-view cells kept their un-normalized `dayDate`.** After a DST
fall-back `add(n, 'day')` carries a stale offset, but the cell's label, its
click target and its event window all derive from that same instant and
therefore agree with each other. #241 noted the resulting one-hour window skew
as a separate, smaller defect on `main`; normalizing only some of those
derivations is what shifted its grid by a whole day. Left alone here for the
same reason: this is a performance change.

**The abstraction costs ~14ns per call.** `overlapsRange` measures ~31ns
through the named helpers against ~17ns with the comparisons inlined, and the
year view is ~12-18% slower than the inlined version (512 plain events under a
timezone: 126 ms to 149 ms). Taken deliberately: against `main`'s 146 632 ms
that is noise, and one documented home for the rule is worth more than 23 ms on
a pathological input. Recorded here so nobody rediscovers it as a mystery.

- **[utils]**: dropped `dayjs.extend(isBetween)`. Zero references anywhere in
  the repo, tests included. Note the configured `dayjs` ships in the public
  Plugin SDK, so a consumer calling `.isBetween()` on it would now throw: worth
  a changelog line.

**Where the timezone cliff actually comes from.** Not dayjs core, and not our
`fixTimezoneOffset` patch alone. dayjs-timezone overrides `startOf` itself, and
for any tz-aware instance it does format -> reparse -> startOf -> `.tz(zone,
true)` on EVERY call, including the no-op `startOf(undefined)`. Every comparator
routes through it (`isBefore` -> `endOf(units)`; `isSame` -> both `startOf` and
`endOf`; `isSameOrAfter` = `isSame || isAfter`, so up to three), which is
exactly the 45µs / 91µs / 135µs measured. Verified in
`node_modules/dayjs/esm/index.js` and `esm/plugin/timezone/index.js`.

**Both halves are already filed upstream and still open**: dayjs#2344 "Very low
performance of comparison functions" (2023-06-19) and dayjs#1399 "isSame
produces incorrect results when DST ended in local zone but haven't ended yet in
the desired timezone" (2021-03-05). dayjs is actively released but carries ~1300
open issues, so a local fix is the only realistic option. Filing a new issue
would duplicate; adding our profile to #2344 would not, since it identifies the
tz plugin's `startOf` as the cause.

**Follow-up: patch the comparators at the dayjs layer.** Overriding
`isBefore`/`isAfter`/`isSame` to compare `valueOf()` when the unit is absent and
the operand is already a Dayjs (falling back otherwise) was prototyped and
measured at 45-135µs -> 12ns, with all 1195 tests passing and no call-site
changes. NOT taken here: it flips answers for stale-offset instances
(`isSame` true -> false, `isAfter` false -> true on two instants an hour apart),
the suite catches none of it, and the configured `dayjs` is public API. Arguably
it is a bug FIX, since dayjs documents unitless comparison as "default
milliseconds" and the current answer violates that. It needs its own change with
those semantics pinned first.

**Follow-up: try dayjs 1.11.23.** We are on 1.11.21. v1.11.22 (2026-08-16)
shipped "timezone compute instance .tz() offset without host DST"
(dayjs#3174, closing #3169), which is the same family of bug as the one
`fixTimezoneOffset` was written to work around: host local DST corrupting the
target zone's offset. If that patch can be deleted, one of the two layers of
cost goes with it. Needs a careful re-read of `docs/timezones.md`.

**Remaining floor.** The year view still spends ~72 ms on 504 tz-aware
`startOf`/`endOf` pairs. `main` paid that too, so it is not a regression. It
is inherent to `dayjs-timezone` and is the next lever if the view needs to get
faster; #241 measured memoizing the offset check at ~1.6x and called it its own
least impactful commit, which matches.

**Not touched**: `useProcessedWeekEvents` and the agenda's grouping structure
needed no restructuring, since fixing the shared predicate fixed them where
they stand. Numeric geometry in `layoutHorizontal`/`layoutVertical` and
virtualization remain unmeasured and out of scope.

# Follow-up: dayjs 1.11.23 and instant-based comparators

Branched off the perf work above (PR #253), not off `main`.

## Changes

- **[deps]**: dayjs 1.11.21 -> 1.11.23 across all five packages that declare it.
  Both releases are timezone-plugin fixes: 1.11.22 "compute instance .tz()
  offset without host DST" (dayjs#3174, closing #3169) and 1.11.23 "prevent
  RangeError for invalid Day.js values" (dayjs#3180).

- **[utils/dayjs]**: new `compareByInstant` plugin. `isBefore`, `isAfter`,
  `isSame`, `isSameOrBefore` and `isSameOrAfter` now answer by epoch
  millisecond when no unit is given AND the operand is already a Dayjs.
  Anything else (a unit, a string, a Date, a number) falls through to the
  original implementation untouched.

  This is a correctness fix as much as a performance one. dayjs documents
  unitless comparison as "default milliseconds", but every comparator routes
  through `startOf`, dayjs-timezone overrides `startOf` with a
  format -> reparse -> `.tz(zone, true)` round-trip, and that re-anchor MOVES an
  instance carrying a stale UTC offset. Two instants an hour apart compared
  equal. Upstream: dayjs#1399 (open since 2021) and dayjs#2344 (open since
  2023).

  Measured, `America/New_York`: `isBefore` 44 957 -> 10 ns, `isSameOrAfter`
  134 739 -> 13 ns, `isSame` 64 794 -> 13 ns. Fallbacks unchanged:
  `isSame(x, 'day')` 101 684 ns, `isBefore('2025-01-01')` 49 282 ns.

## Files Modified

- `packages/{utils,types,calendar,playground}/package.json`, `apps/website/package.json` - dayjs ^1.11.23
- `packages/utils/src/dayjs.ts` - `compareByInstant`, extended last so it wraps the plugin-installed comparators
- `packages/utils/src/dayjs.test.ts` - six cases pinning instant semantics, stale-offset ordering, and every fallback

## Notes

**`fixTimezoneOffset` CANNOT be deleted.** That was the hope behind the upgrade.
Tested against raw upstream 1.11.23 with no patch: walking all 365 days of 2025
in six zones, calling `startOf('day')` and `endOf('day')` and checking the
reported offset against `Intl`, 4 380 checks produced 4 mismatches on hosts
UTC / Europe/Paris / Europe/London and 12 on America/New_York, always on a DST
transition day. With our patch: 0 mismatches on every host tried. So the bug it
works around is still live upstream and the patch is load-bearing. The upgrade
is still worth taking on its own merits.

**Tests were written before the flip, deliberately.** The previous session's
prototype of this change passed all 1 195 tests while silently changing
`isSame` from true to false on drifted instances, which is exactly the shape
`.agents/rules/change-impact.md` warns about: a behaviour nobody had pinned.
The two cases that now fail against the old implementation are the ones worth
having.

**The instant comparators in `@ilamy/utils/helpers` are now redundant for
performance**, since `a.isBefore(b)` and `isBefore(a, b)` both cost ~12ns. They
are kept for now because they read explicitly at the call site and because
reverting PR #253's call sites would be churn. Worth revisiting once this
lands. `dayKey` and `isSameDay` are NOT redundant: `isSame(x, 'day')` carries a
unit, so it still falls back to dayjs at ~101µs.

**Not changed**: the ~10 unit-ed comparison call sites (`isSame(x, 'day')`,
`isBefore(x, 'month')`) in the event form, the shadcn calendar and the
playground. All are cold paths, and the unit-ed forms ask a different question.
