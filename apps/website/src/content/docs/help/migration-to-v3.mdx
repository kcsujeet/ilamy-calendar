---
title: Migrating to v3
description: Upgrade from @ilamy/calendar v2 to v3, where an event's `end` becomes exclusive.
slug: docs/help/migration-to-v3
---

v3 contains one breaking change. If your calendar only shows timed events
inside a single day, you can upgrade without touching anything.

## What changed

An event's `end` is now **exclusive**: an event runs up to, but not including,
the instant you give it.

```tsx
// v2: painted 13 and 14 January
// v3: paints 13 January only
{ start: '2025-01-13T00:00:00.000Z', end: '2025-01-14T00:00:00.000Z' }
```

This matches [RFC 5545 §3.6.1](https://www.rfc-editor.org/rfc/rfc5545#section-3.6.1),
which calls DTEND "the non-inclusive end of the event", and the
[Google Calendar API](https://developers.google.com/workspace/calendar/api/v3/reference/events),
which documents `end` the same way. v2's inclusive reading was a deviation from
both, and it is the reason the same event could be exported to another calendar
and come back a day longer.

## Who is affected

| You use | Affected |
|---|---|
| Timed events inside one day | No |
| An inclusive-style end such as `23:59` | No — that instant falls *during* the day, so it still renders on the day it names |
| Multi-day events ending at midnight | **Yes** — the bar is one day shorter |
| All-day events | **Yes** — see below |
| `onCellClick` and reading `info.end` | **Yes** — see below |

## The three changes in detail

- **`end` is exclusive on date grids.** An event runs up to, but not including, its `end`, matching [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545) and the [Google Calendar API](https://developers.google.com/workspace/calendar/api/v3/reference/events). An event from `2025-01-13T00:00` to `2025-01-14T00:00` covers Jan 13 only; previously it also painted Jan 14. To keep a two-day bar, end it during the second day (`2025-01-14T23:59`) or at the following midnight (`2025-01-15T00:00`). Timed events inside a day are unaffected, and an inclusive-style end such as `23:59` still renders on the day it names, because that instant falls during the day.

- **All-day events store an exclusive end.** The built-in form now writes the midnight after the last covered day rather than `23:59`, so a one-day all-day event exports as `DTSTART;VALUE=DATE:20250804` / `DTEND;VALUE=DATE:20250805`, which is what the RFC requires. The form still shows you the last covered day, and an existing event ending at `23:59` is read as the inclusive value it is, so old data keeps displaying correctly.

- **Day cells report an exclusive range.** `CellInfo.end` from `onCellClick` (and the `data-end` attribute plugins read) is now the next midnight rather than `23:59`, matching the hour and 15-minute cells, which already ended on the next slot boundary.

## What to do

1. Audit multi-day and all-day events: a bar that used to reach its `end` day
   now stops the day before. To keep a two-day bar, end it during the second day
   (`2025-01-14T23:59`) or at the following midnight (`2025-01-15T00:00`).
2. If you read `CellInfo.end` in an `onCellClick` handler, it is now the next
   midnight rather than `23:59`. Code that subtracted a second to get "the end
   of the day" should stop doing so.
3. Existing stored events are not migrated for you, and they do not need to be:
   an event ending at `23:59` is read as the inclusive value it is and keeps
   displaying as it did.

## Checklist

- [ ] Audit multi-day and all-day events for the exclusive `end`: a bar that used to reach its `end` day now stops the day before.
- [ ] Check any `onCellClick` handler that reads `info.end`.
- [ ] Re-export to iCal if you compare against another calendar — the exported
      `DTEND` is now the RFC's exclusive value.
