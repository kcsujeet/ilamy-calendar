# @ilamy/perf: runtime benchmark

A repeatable benchmark that drives the calendar through the same scenarios on
two builds (`origin/main` and the stack top) and reports medians, p90s, noise,
absolute budget verdicts and the delta between the builds. It is **not** part of
the e2e gate and nothing here is published.

```bash
# both builds + comparison (baseline worktree must live outside this checkout)
PERF_BASELINE=/somewhere/perf-main-baseline bun run perf:both

# one build only (build the package and the app first)
bun run build                         # repo root: builds packages/calendar/dist
cd apps/perf && bunx vite build
PERF_LABEL=stack PERF_PORT=4501 bun run perf
PERF_REPS=1 PERF_SCENARIOS=week-500-slot15 PERF_THROTTLES=1 bun run perf   # a quick look
bun run perf:compare                  # results/comparison.md from results/main.json + stack.json
```

Environment: `PERF_REPS` (default 5), `PERF_SCENARIOS` (comma separated ids),
`PERF_THROTTLES` (default `1,4`), `PERF_CELL_BUDGET_MIN` (default 10; see below),
`PERF_LABEL`, `PERF_PORT`, `PERF_OUT`. For `perf:both`: `PERF_BASELINE`
(required), `PERF_KEEP_BASELINE`, `PERF_SKIP_BUILD`, `PERF_FRESH`,
`PERF_ONLY` (`stack` or `main`), `PERF_CONCURRENT`.

## What it measures

The app (`src/`) renders `IlamyCalendar` from a scenario in the URL
(`/?s=<id>`), using only props that exist in v3.2.1 so the identical app runs on
both builds. It imports the **built** package (`packages/calendar/dist`) the way
a consumer does, as a minified production bundle, with `react-dom/client`
swapped for `react-dom/profiling`, because [`<Profiler>`] reports nothing in a
plain production build.

Scenarios (`src/plan.ts`, events generated by a seeded PRNG in `src/scenarios.ts`):

| id | what |
|---|---|
| `month-2000` | month, 2,000 events over March and April |
| `week-500-slot15` | week, 500 timed events, 15 minute slots |
| `vres-week-50` | vertical resource week, 50 resources, slot 15 (#300) |
| `vres-week-30-slot60`, `-slot30`, `-slot15` | vertical resource week, 30 resources, 60/30/15 minute slots |
| `hres-day-200`, `hres-day-500` | horizontal resource day, 200/500 resources, 5 events each |
| `hres-week-200`, `hres-week-500` | horizontal resource week, 200/500 resources, 5 events each |
| `year-5000` | year view, 5,000 events |
| `recurring-month` | month, recurrence plugin, 50 daily series |

Every scenario also has one `PERF SUBJECT` event that the interactions grab.
Interactions (`tests/perf.spec.ts`), each on a fresh page per repetition:

- **mount**: app script start to the subject bar being on screen and one painted frame.
- **next/prev x10**: alternating Next/Previous clicks; input to next paint, per click.
- **view switch**: to each of the scenario's other views and back; input to next paint.
- **open event form**: a real pointer click on the subject; click to the paint showing the dialog.
- **resize**: a real pointer drag of the end handle in 12 steps, then the drop (stack only; main has no resize).
- **drag**: a real pointer drag of the subject across about 10 cells in 20 steps, then the drop.
- **auto-scroll**: the subject held at the bottom edge of its scroll container for 2 s while dnd-kit scrolls.

Drags and resizes are validated: if the subject did not actually move/grow, the
repetition records an error instead of a fast number.

Recorded per interaction: React commits and summed `actualDuration` from the
`<Profiler>`; CDP `Performance.getMetrics` deltas (`ScriptDuration`,
`LayoutDuration`, `RecalcStyleDuration`, `TaskDuration`, `JSHeapUsedSize`);
`longtask` entries. Per pointer step: input-to-next-paint, JS work (CDP
`ScriptDuration` delta) and main-thread task time (`TaskDuration` delta). For
auto-scroll, 100 ms windows divided by the rAF callbacks counted in the window
give per-frame JS and task time.

Input-to-next-paint is `event.timeStamp` of the input to the first task after
the next frame's paint (`requestAnimationFrame` then `setTimeout(0)`), started
inside a capture-phase listener so no Playwright round trip is included. It
includes waiting for the next frame, so it has a floor of up to one frame
(16.7 ms); that is why the per-step *budgets* are judged on JS and task time, not
on paint latency.

Each scenario runs at CPU throttle 1x and 4x (`Emulation.setCPUThrottlingRate`),
5 repetitions. Heavy scenarios take minutes per repetition, so a
scenario x throttle cell stops adding repetitions once the next one would
exceed `PERF_CELL_BUDGET_MIN`; it always runs at least one. The repetition
count per cell is printed in the report (`reps main/stack`). With n=1 the
min-max is meaningless.

Pinned: viewport 1280x900, `timezoneId: UTC` and `timezone="UTC"` on the
calendar, `en-US`, light scheme, the date the calendar opens on, one Playwright
worker. The clock is **not** faked: `page.clock` replaces `performance.now` and
`requestAnimationFrame`, which this benchmark times with. "Today" is therefore
the real date and is not on screen (the calendar opens on 12 March 2025).

## Budgets (owner-set), applied to every row

| class | rows | budget |
|---|---|---|
| continuous | drag-over steps, resize steps, auto-scroll frames | JS per step/frame p90 <= 10 ms at 1x, <= 16 ms at 4x; main-thread task per step/frame p90 <= 16 ms at 1x and at 4x |
| continuous | any drag, resize or auto-scroll | no task > 50 ms at 1x |
| discrete | next/prev, view switch, drop commit, resize commit, open event form | input to next paint p90 <= 100 ms at 1x, <= 200 ms at 4x |
| mount | first stable paint | no standard; reported, flagged above 1,000 ms at 4x |

Sources: RAIL, <https://web.dev/articles/rail> (a frame in 10 ms and an absolute
maximum of 16 ms; respond or complete a transition within 100 ms; idle work in
chunks of 50 ms) and INP, <https://web.dev/articles/inp> ("good" is 200 ms or
less). Interpretation choices, stated so they can be overruled: the 4x "<= 16 ms
p90" is applied to both JS and task time; p90 is nearest-rank over every sample
pooled across repetitions; for a one-sample-per-repetition metric (drop commit,
resize commit, open form) p90 over 5 repetitions is effectively the maximum.

The delta between builds is flagged WORSE only when the stack is slower by more
than 10% **and** more than 5 ms.

## Finding a cause

When a row regresses, profile it on a readable build:

```bash
PERF_NO_MINIFY=1 bunx vite build --outDir dist-profile
bunx vite preview --outDir dist-profile --port 4601 --strictPort &
PORT=4601 SCENARIO=month-2000 MODE=profile bun scripts/profile-drag.ts              # drag steps, split into cell-crossing and plain
PORT=4601 SCENARIO=week-500-slot15 INTERACTION=nav bun scripts/profile-interaction.ts  # mount, nav or drop
```

Both print self time, inclusive time and the nearest React component per
function; `profile-drag.ts` with `MODE=count` counts renders per component. Confirm
a suspect by stubbing it out, re-measuring, and reverting the stub.

## Known limits

- Headless Chromium on one machine: absolute numbers are not portable; only a
  comparison of builds measured under identical conditions means anything.
  Measured concurrently, one build's numbers were 20-35% worse than alone (a
  control we ran), so `perf:both` runs the builds one after the other by default
  (`PERF_CONCURRENT=1` opts in to the faster, less fair mode).
- CPU throttling slows JS and layout but not the compositor or raster threads.
- `JSHeapUsedSize` deltas depend on when GC runs and are not a leak measure.
- Per-step JS/task time includes a few hundred microseconds of the measurement's
  own `Performance.getMetrics` and `evaluate` calls, identically on both builds.
- The `<Profiler>` build adds a little overhead to React, identically on both builds.
